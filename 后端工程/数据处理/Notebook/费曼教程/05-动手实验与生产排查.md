# 📌 动手实验与生产排查

本实验使用四条虚构车辆事件，把前面的心智模型变成可观察结果。示例只依赖 Python 标准库，不需要集团表、Fileset 权限或 Spark；跑通后再把输入层替换成真实平台数据。

学完本篇，你应该能执行示例 Notebook，预测参数变化后的输出，并沿“会话、代码版本、输入输出、依赖、资源”顺序排查生产失败。

## 📄 实验文件与目标

示例目录包含：

```text
examples/
├── hard-braking-demo.ipynb
└── vehicle-events.csv
```

输入 CSV 有四条事件。默认参数是：

```python
event_date = "2026-08-12"
threshold_kmh = 20
window_seconds = 2
```

先预测：输出 `scene-manifest.csv` 会包含哪些事件？根据输入数据计算速度差，答案应是 `E101`、`E103`。

## 📄 运行方式一：使用集团 Notebook 页面

1. 打开“数据工场 > 查询 > Notebook”，然后新建 Notebook。
2. 把 [hard-braking-demo.ipynb](examples/hard-braking-demo.ipynb) 和 [vehicle-events.csv](examples/vehicle-events.csv) 放在同一项目目录。
3. 创建并连接 Runtime。
4. 从上到下运行全部 Cell。
5. 确认页面输出候选 ID，并在 Notebook 同目录检查 `scene-manifest.csv`。

不同页面版本对导入 `.ipynb`、上传项目文件的入口可能不同。入口变化时保持不变的目标是：两个文件进入同一 CWD，Runtime 能读取相对路径 `vehicle-events.csv`。

```python

```

先只运行最后一个输出 Cell。它仍可能使用旧 `candidates`，这不能证明新阈值没有效果。正确实验是重启 Runtime，再运行全部 Cell。期望输出只剩 CSV 表头，因为两条候选的速度下降都等于 30。

再把日期改成 `2026-08-13`、阈值恢复为 20，运行全部。期望命中 `E104`。

## 📄 把本地输入替换成 Spark 表

进入真实空间后，保留参数和输出契约，把读取 CSV 的 Cell 替换为：

```python
from pyspark.sql import functions as F

events = (
    spark.table("<catalog>.<database>.<vehicle_event_table>")
    .where(F.col("event_date") == event_date)
    .where(F.col("window_seconds") == window_seconds)
)

candidates = (
    events
    .withColumn(
        "speed_drop_kmh",
        F.col("speed_before_kmh") - F.col("speed_after_kmh"),
    )
    .where(F.col("speed_drop_kmh") >= threshold_kmh)
)
```

先用真实表的 Schema 替换占位字段，再用 `limit(20).toPandas()` 抽样核对。数据量增大后，输出应直接写表或 Fileset，避免全部收回 Driver。

## 📄 把示例发布成离线作业

在平台上完成：

1. 将第一个 Cell 标记为调度参数。
2. 保存并在干净 Runtime 中运行全部。
3. 复制 Notebook 与必要输入文件到 AI 数据开发项目目录。
4. 新建 Notebook 作业，选择 `.ipynb` 入口文件。
5. 设置 `Arguments`：`-p event_date 2026-08-12 -p threshold_kmh 20 -p window_seconds 2`。
6. 把 `scene-manifest.csv` 的实际项目路径加入 `outputFiles`。
7. 选择 Spark 或 Ray、基础环境和资源配置。
8. 设置超时与需要的重试次数，校验后上线工作流。
9. 执行一次，查看最终 Notebook、日志和输出文件。

第一次执行只用四条样本，先验证参数注入和文件传递。再替换成小日期分区，最后才扩大范围。每一步只增加一种未知因素。

## 📄 按层排查，不从业务代码里猜

| 现象 | 第一证据 | 处理方向 |
| --- | --- | --- |
| Cell 报 `NameError` 或结果忽变 | Runtime 是否重启、依赖 Cell 是否执行 | 从顶部运行全部，检查变量定义顺序 |
| Notebook 无法运行 | Runtime 状态与连接状态 | 启动 Runtime，再连接 Notebook |
| 重启后 `ModuleNotFoundError` | 依赖是否只通过 `%pip` 动态安装 | 在作业 Python 依赖中正式声明 |
| 交互结果已变，定时结果未变 | 作业中的 Notebook 文件和工作流 revision | 对比、更新文件并重新上线 |
| 节点成功但下游找不到 CSV | CWD 实际文件路径与 `outputFiles` 键 | 统一生成路径、声明路径和引用键 |
| Driver 内存不足 | 是否调用无限制的 `collect()` / `toPandas()` | 限制预览，直接分布式写出或逐步迭代 |
| `ExecutorLostFailure`、exit code 137 | Executor 日志和内存指标 | 检查单 Task 数据、堆内/堆外内存和并行度 |
| 内网请求成功、公共 URL 失败 | 网络边界 | 集团文档说明 Runtime 不开放公共互联网访问 |
| Flow 校验类型不存在 | 最新 Notebook 插件 Schema | 使用 Schema 返回的任务类名和字段 |

集团常见问题文档给出的 Executor OOM 调整示例是增加 `spark.executor.memoryOverhead`，并提示堆外内存与 Executor 内存之和不超过 16G。这个上限属于当时平台约束，处理真实作业时还要核对当前队列与 Schema。

Spark 的 Stage、Task、Shuffle、数据倾斜和 OOM 排查见 [Spark 可靠性与生产排查](../../Spark/费曼教程/06-可靠性与生产排查.md)。

## 📄 最终闭卷复述

不看教程，向一位只会 Java 的同事讲清下面这次运行：

> 工程师在 Notebook 开发页面用默认日期调试急减速规则，复制到 AI 数据开发，调度传入第二天日期，Spark 读取事件表，沿 `raw_log_path` 生成候选清单，下游节点读取 CSV。后来工程师修改阈值但忘记更新作业，定时结果仍是旧规则。

复述中应依次出现：

1. `.ipynb` 文件与 Runtime 会话状态。
2. 表与 Fileset 的不同责任。
3. 交互文件到离线作业的快照边界。
4. 默认参数 Cell 与运行时注入 Cell。
5. CWD、`outputFiles` 和下游引用。
6. 工作流 revision、execution 和业务结果证据。

缺少哪一步，就回到负责它的章节重新画一次对象与箭头。能在不使用“平台就是自动跑 Notebook”这类含糊句子的情况下讲完整，才算建立了可迁移的心智模型。
