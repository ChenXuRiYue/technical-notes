# 📌 交互式完成一次场景挖掘

急减速规则很少一开始就完全正确。工程师会先查看几条事件，调整阈值，核对命中的原始片段，再决定是否批量处理一天或一个月的数据。Notebook 让样本、规则、运行结果和调整记录留在同一个文件中。

学完本篇，你应该能用 Cell 完成“确认输入、验证规则、限制预览、固化输出”四个动作，并解释每一步为什么存在。

## 📄 第一步：启动并连接 Runtime

打开“数据工场 > 查询 > Notebook”，新建或选择一份 Notebook。运行代码前：

1. 新建或选择 Runtime。
2. 配置基础环境和计算资源。
3. 启动 Runtime，等待状态进入运行中。
4. 将 Notebook 连接到该 Runtime。
5. 用一个最小 Cell 验证连接：

```python
print("runtime-ready")
```

先让最小动作成功，再读取真实数据。这样连接失败、环境失败和业务代码失败不会混在同一条日志中。

## 📄 第二步：定义本次实验口径

第一个 Python Cell 只放参数默认值：

```python
event_date = "2026-08-12"
threshold_kmh = 20
window_seconds = 2
```

此时这些值既方便交互调试，也为后续离线参数化留下稳定入口。不要在这个 Cell 中读取表、写文件或发请求，参数注入机制将在 [参数 Cell 的注入机制](04-参数-Cell-注入.md) 中解释。

## 📄 第三步：先在小样本上证明规则

先用内存中的三条样本验证计算：

```python
events = [
    {"event_id": "E101", "event_date": "2026-08-12", "before": 72, "after": 42},
    {"event_id": "E102", "event_date": "2026-08-12", "before": 50, "after": 41},
    {"event_id": "E103", "event_date": "2026-08-12", "before": 90, "after": 60},
]

def is_candidate(event):
    speed_drop = event["before"] - event["after"]
    return event["event_date"] == event_date and speed_drop >= threshold_kmh

candidates = [event for event in events if is_candidate(event)]
[event["event_id"] for event in candidates]
```

预测输出后再运行。阈值是 20，因此输出应为：

```text
['E101', 'E103']
```

改变一个条件：把 `threshold_kmh` 改成 `31`，只重跑最后一个 Cell。结果会变化吗？不会，因为 `candidates` 已经在前一个 Cell 中计算完成。你需要先重跑参数 Cell，再重跑生成 `candidates` 的 Cell。这正是 Runtime 状态会掩盖依赖顺序的例子。

## 📄 第四步：替换成平台表读取

小样本证明规则后，再把输入替换为真实表。下面使用教学表名和 PySpark API：

```python
from pyspark.sql import functions as F

events = (
    spark.table("autodrive.vehicle_events")
    .where(F.col("event_date") == event_date)
    .where(F.col("window_seconds") == window_seconds)
)

candidates = (
    events
    .withColumn(
        "speed_drop_kmh",
        F.col("speed_before_kmh") - F.col("speed_after_kmh"),
    )
    .where(F.col("speed_drop_kmh") >= threshold_kmh)
    .select("event_id", "vehicle_id", "speed_drop_kmh", "raw_log_path")
)
```

这段代码主要构建 DataFrame 计划。预览时限制行数：

```python
candidates.orderBy(F.col("speed_drop_kmh").desc()).limit(20).toPandas()
```

生产写出时让 Executor 直接写表或文件，不要先把所有结果 `collect()` 到 Driver。

## 📄 第五步：固化可被下游消费的输出

本地小样本可以用 Python 标准库写 CSV：

```python
import csv

with open("scene-manifest.csv", "w", newline="", encoding="utf-8") as output:
    writer = csv.DictWriter(output, fieldnames=["event_id", "raw_log_path"])
    writer.writeheader()
    for event in candidates:
        writer.writerow({
            "event_id": event["event_id"],
            "raw_log_path": f"gvfs://fileset/autodrive/raw/{event['event_id']}/",
        })
```

`with open(...)` 会在代码块结束时关闭文件，接近 Java `try-with-resources`、Rust RAII 或 Go `defer Close()` 的目标。

离线 Notebook 作业规定：**主 Notebook 所在目录就是当前工作目录 CWD**。相对路径 `scene-manifest.csv` 会写在该目录下；作业的 `outputFiles` 必须用平台实际生成路径声明这个文件，后续节点才能引用。

## 📄 依赖与 Shell 的边界

交互 Runtime 支持在 Cell 中动态安装依赖：

```python
%pip install pandas
```

`%pip` 是 IPython Magic，不是 Python 语法。动态安装只对当前 Runtime 有效，Runtime 重启后需要重新安装。准备离线生产时，应在 Notebook 作业的 Python 依赖配置中声明必要包，避免作业依赖一次交互会话留下的环境。

平台也支持 `%%sh` 或 `!command` 执行 Shell。它们适合查看目录和做受控的文件操作，但 Shell 副作用同样要考虑工作目录、权限和作业重试。

## 📄 一次干净验证

调试完成后执行：

1. 保存 Notebook。
2. 重启或切换到一份干净 Runtime。
3. 从上到下“运行全部”。
4. 检查候选数量、样本内容和输出文件。
5. 记录参数默认值与数据日期。

这一步证明结果来自文件中可见的代码顺序，而不是旧 Runtime 遗留变量。

## 📄 费曼检查

向一位熟悉单元测试的同事解释：

> 为什么先用三条内存样本，再替换成 Spark 表？为什么最后还要在干净 Runtime 中运行全部？

答案应出现“快速验证规则”“控制输入规模”“排除旧会话状态”三个因果点。遗漏其中一个时，回到对应步骤重新解释它防止了哪类错误。
