## 📄 从 HTTP 请求追踪到结果 Snapshot

不看教程，补全下面的身份与结果证据：

```text
HTTP 请求
  -> Spring 创建 ______
  -> Submitter 绑定 ______
  -> Spark 选择 input ______
  -> Driver 划分 Stage，Executor 执行 ______
  -> Iceberg 发布 output ______
  -> Reconciler 回写业务终态
```

参考链路是：

```text
jobId -> applicationId -> Snapshot -> Task -> Snapshot
```

其中前两个是任务身份，Task 是一次分区计算，两个 Snapshot 分别固定输入表版本和证明输出表版本已经发布。

## 📄 综合故障题

日报任务 `J42` 的证据如下：

```text
Spring: RUNNING
application_42: SUCCEEDED
Spark: 所有 Task 成功
存储: 有 12 个新 Parquet
Iceberg .snapshots: 没有新 Snapshot
```

先预测最可能的失败边界，再展开答案。

<details>
<summary>参考推理</summary>

Executor 已经写出文件，而 Iceberg 没有新 Snapshot，问题集中在 Driver 汇总提交信息、生成 Iceberg 元数据或 Catalog 提交阶段。`Application SUCCEEDED` 与“没有新 Snapshot”互相矛盾，还要检查 Job 是否把表提交作为成功条件，或者是否吞掉提交异常后正常退出。

这 12 个 Parquet 尚未进入有效表版本。使用 Iceberg 的安全维护与重试流程处理，不手工把文件塞进表元数据。

</details>

## 📄 改变条件再推导

把条件改为：

```text
Spring: RUNNING
application_42: SUCCEEDED
Iceberg: output Snapshot S901 已发布
质量检查: M01=2/100.00, M02=1/45.00
```

Spark 计算和 Iceberg 提交已经完成，故障边界收窄到 Reconciler 的状态校准。此时应修复状态回写，不重新提交 Application。

再改变一个条件：MQ 将 `J42` 投递两次。完整答案需要同时说明：Spring 用幂等键稳定创建 `jobId`，Submitter 用 `jobId` 获取唯一提交权，Spark 输出采用可重复执行的分区覆盖策略。
