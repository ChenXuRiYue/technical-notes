# 📌 可靠性、运维与生产排查

整条链路有多个独立的进度与提交点。排查时先用身份把各层串起来，再在确定的层内查指标和日志：

```text
jobId
  -> Outbox / MQ eventId
  -> applicationId
  -> Spark Job / Stage / Task
  -> input Snapshot / output Snapshot
  -> Data File
```

## 📄 任务卡住时按状态边界排查

| 任务表现 | 先查 | 可能原因 |
| --- | --- | --- |
| 长时间 `PENDING` | Outbox 是否存在、是否发布、MQ 是否堆积 | 事件没写入、Publisher 停止、消费赶不上 |
| 长时间 `SUBMITTED` | `applicationId` 在集群中的状态 | 队列资源不足、镜像拉取失败、Driver 未启动 |
| `RUNNING` 但无进度 | Spark UI 中最慢 Stage 和 Task | 数据倾斜、远程存储慢、Shuffle Spill、GC |
| Application 成功，任务仍 `RUNNING` | Reconciler、结果表 Snapshot 和质量检查 | 回调丢失、校准器停止、结果证据不足 |
| `FAILED` | 分类失败阶段 | 参数、依赖、资源、计算、存储或 Catalog 提交失败 |

定时校准器对 `SUBMITTED`、`RUNNING` 和 `CANCEL_REQUESTED` 记录重查集群状态。对超过业务时间预算的任务发出告警，并保留自动取消或人工处理的明确边界。

## 📄 重试要在三层都成立

### 🔖 任务创建幂等

同一 `Idempotency-Key` 返回同一 `jobId`，防止客户端超时重试创建两份任务。

### 🔖 Application 提交幂等

Submitter 使用 `jobId` 获取唯一提交权，并将平台的幂等键与 `jobId` 绑定。超时后先查既有运行，再决定是否提交。

### 🔖 输出数据幂等

日报 Job 动态覆盖自己生成的 `report_date` 分区，重跑产生同一份逻辑结果。对增量明细、`MERGE INTO` 或多表结果，需要另行定义业务键、版本和提交顺序。

三层中任意一层缺少幂等性，重试都可能变成重复 Application 或重复数据。

## 📄 Spark 慢任务怎样查

### 🔖 先看扫描量

- Iceberg 分区裁剪是否命中日期范围。
- 列裁剪后是否只读 `created_at`、`merchant_id`、`amount`。
- 是否有大量小文件，使计划和调度成本超过实际扫描。

### 🔖 再看 Stage 与 Task 分布

- Task 耗时是整体都慢，还是少数尾部 Task 特别慢。
- Shuffle Read/Write、Spill、GC 和输入记录数是否集中在少数 Task。
- 失败重试是否反复发生在同一分区。

### 🔖 最后调整计划或资源

| 现象 | 调整方向 |
| --- | --- |
| 大量极小 Task | 合理合并扫描分区，治理 Iceberg 小文件 |
| 每个 Task 输入过大 | 增加合理并行度，核对文件分割与 Shuffle 分区 |
| 少数热点 key | 预聚合、加盐拆分、单独处理热点 |
| 广播表超大 | 修正统计或 Join 策略，避免 Executor 内存溢出 |
| 频繁 Spill / GC | 先减少每 Task 数据与宽对象，再评估 Executor 内存 |

资源调整与计划修正要用指标验证。盲目增加 Executor 会增加集群成本，却不会消除热点 key、不可裁剪的全表扫描或数以万计的小文件。

## 📄 Iceberg 写入问题怎样查

| 现象 | 核心问题 | 查证据 |
| --- | --- | --- |
| Executor 有输出，表无新数据 | Snapshot 提交是否成功 | Driver 提交日志、Catalog 错误、`.snapshots` |
| 提交冲突 | 是否有并发写者改变同一范围 | Snapshot 时间线、作业参数、冲突类型 |
| 存储中有无引用新文件 | 写文件后是否在提交前失败 | 任务时间窗口、有效元数据引用、安全孤儿文件扫描 |
| 表读取越来越慢 | 小文件、Manifest 和 Snapshot 是否膨胀 | 文件数量/大小分布、元数据表、规划耗时 |

小文件合并、Manifest 重写、Snapshot 过期和孤儿文件删除是不同维护操作。它们的安全参数、保留窗口与执行顺序见 [Iceberg 生产运维与版本治理](../../../数据存储/Iceberg/教程/06-生产运维与版本治理.md)。

## 📄 监控与日志最小集

### 🔖 Spring 任务层

- 各状态数量与停留时间。
- Outbox 未发布数量与最旧事件年龄。
- Submitter 提交成功/失败/不确定次数。
- Reconciler 落后时间与状态修正次数。

### 🔖 Spark 计算层

- Application 排队、启动、运行和结束耗时。
- Stage 耗时、失败次数与尾部 Task 分布。
- 输入字节、输出字节、Shuffle Read/Write、Spill 和 GC。
- Executor 丢失、OOM 和 Task 重试。

### 🔖 Iceberg 结果层

- Snapshot 提交耗时、冲突与重试。
- 每次提交的新文件数、平均大小和行数。
- 目标分区的结果行数、金额和非空检查。
- Snapshot 与数据文件保留量。

所有结构化日志至少带 `jobId`，获得后再带 `applicationId`。Driver 和结果校验日志带输入/输出表名、日期范围和 Job 版本，不记录密钥与完整敏感数据。

## 📄 故障推演

**场景：** 任务库显示 `RUNNING` 两小时，集群中 Application 已经 `SUCCEEDED`，结果表也有新 Snapshot。

推理顺序：

```text
Application 成功
  + 结果 Snapshot 存在
  -> 计算与表提交大概已完成
  -> 问题收窄到状态回写/校准
  -> 查 Reconciler 调度、查询权限、带条件更新与迟到事件
```

此时重新提交 Spark Application 会扩大问题。正确动作是修复可恢复的状态校准链。
