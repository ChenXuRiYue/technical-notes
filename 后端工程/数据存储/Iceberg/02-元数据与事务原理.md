# 📌 Iceberg 元数据与事务原理

Iceberg 用一棵分层元数据树描述一张表。Catalog 提供当前 Metadata JSON 的入口，Metadata JSON 记录表结构和 Snapshot 历史，当前 Snapshot 通过 Manifest List 与 Manifest 列出有效的 Data File 和 Delete File。查询规划器沿这条链路选定表版本，并利用分区摘要和列统计裁剪文件。

## 📄 这一篇要解决什么问题

上一节把 Snapshot 简化成 `[A, B, C]`。真实表可能有百万个数据文件。Iceberg 将“表的说明书”和“文件清单”拆成多层，并在清单中保存统计信息，让查询逐层缩小候选范围。

这一篇只追两条路径：

```text
读：表名 -> 当前版本 -> 文件清单 -> 候选数据文件
写：读取旧版本 -> 生成新文件 -> 尝试发布新版本
```

学完后应能画出这两条路径，并解释为什么新写的数据文件先落盘、最后发布元数据，读者仍不会看到半成品。

## 📄 先认识“元数据”

**元数据是描述数据的数据。** `A.parquet` 中的用户事件是业务数据；“A 文件有 100 万行、`event_time` 最小为 8 月 1 日、属于哪个 Snapshot”是元数据。

JSON 是一种文本数据表示格式，Metadata JSON 就是 Iceberg 用 JSON 编码的一版表级说明书。Manifest List 和 Manifest 因为数量可能很大，使用 Avro 二进制格式保存，但它们的角色仍是元数据。

可以把层级理解为一本书的检索系统：

| Iceberg 对象 | 检索类比 | 为什么不直接读数据文件 |
| --- | --- | --- |
| Metadata JSON | 选择哪一版总目录 | 先确定表版本和规则 |
| Snapshot | 选择某次发布后的馆藏状态 | 时间旅行需要明确版本边界 |
| Manifest List | 总目录中的分册目录 | 先排除整批不相关清单 |
| Manifest | 分册中的条目和摘要 | 再排除不可能命中的文件 |
| Data File | 真正的书 | 只打开剩余候选文件 |

这个类比用于理解逐层缩小范围；真实元数据还保存 Schema ID、分区规则、序列号等精确信息。

## 📄 元数据树

```text
Catalog
└── table -> metadata/vN.metadata.json
    ├── Schema / Partition Spec / Sort Order
    ├── Snapshot Log
    └── Current Snapshot
        └── Manifest List
            └── Manifest Files
                ├── Data Files
                └── Delete Files
```

| 对象 | 保存或表达的内容 | 生命周期提示 |
| --- | --- | --- |
| Catalog | “表名 -> 当前 Metadata JSON”的入口，以及原子更新能力 | 每次加载表都从这里获得权威入口 |
| Metadata JSON | 表级元数据版本、Schema、分区规则、排序规则、属性、快照历史和当前快照 | 元数据修改也可产生新版本 |
| Snapshot | 一次数据变更提交后可见的文件集合 | 时间旅行、回滚和增量扫描的版本边界 |
| Manifest List | 某个 Snapshot 使用哪些 Manifest，以及它们的分区摘要 | 每个 Snapshot 通常有自己的 Manifest List |
| Manifest | Data/Delete File 清单、分区值、列上下界、空值数等统计 | 未变化的 Manifest 可被新 Snapshot 复用 |
| Data File | 真正的 Parquet、ORC 或 Avro 业务数据 | 通常按不可变文件处理 |
| Delete File | v2 表的位置删除或等值删除表达 | 查询时与 Data File 合并解释 |

### 🔖 Metadata JSON 与 Snapshot

Metadata JSON 是完整的表级元数据版本，其中包含 Schema、分区规则、表属性、Snapshot 历史和当前 Snapshot 引用。Snapshot 表示一次数据变更提交后的可见文件集合。修改 Schema、表属性或 Branch/Tag 引用会生成新的 Metadata JSON；只有形成新的数据文件视图时，才需要新 Snapshot。

Manifest List 与 Manifest 是采用 Avro 编码的 Iceberg 元数据文件，内容是 Manifest 和 Data/Delete File 的清单与统计。Avro Data File 则保存表中的业务行，两者的文件角色不同。

## 📄 查询时

```text
1. SQL 中的表名交给 Catalog
2. Catalog 返回当前 Metadata JSON 入口
3. 引擎选择当前或指定的 Snapshot
4. 用查询条件和摘要裁剪 Manifest
5. 用分区值、列统计裁剪 Data File
6. Worker 读取候选 Data File
7. 应用 Delete File 和剩余过滤条件
8. 返回投影、聚合或 Join 后的结果
```

Worker 是实际读取和计算数据的工作节点；Task 是分配给 Worker 的一份任务。投影只返回查询选中的列，聚合把多行汇总为统计值，Join 按条件连接多张表。这些计算由计算引擎执行；Manifest 为规划阶段提供文件清单和统计信息。

“裁剪”是将查询条件与 Manifest 中的分区摘要、列上下界和空值数等统计比较，先排除无命中可能的 Manifest 和 Data File。这是文件级粗粒度索引；被保留的候选文件再由引擎读取，执行行级过滤。

### 🔖 一个裁剪示例

假设两个 Data File 的 `event_time` 统计如下：

| 文件 | lower_bound | upper_bound |
| --- | --- | --- |
| A.parquet | 2026-08-01 00:00:00 | 2026-08-01 23:59:59 |
| B.parquet | 2026-08-02 00:00:00 | 2026-08-02 23:59:59 |

查询条件为 `event_time >= '2026-08-02'` 时，规划器可以证明 A 不可能命中，因此无需打开 A。若统计范围跨越查询边界，则只能保留该文件并在读取后继续过滤。

再预测一个跨边界的情况：若 A 的范围是 8 月 1 日到 8 月 3 日，文件级上下界表明它可能命中，所以仍要读取 A，即使真正符合条件的记录只有一行。统计裁剪只排除能够确定无结果的文件。

### 🔖 从慢查询定位层次

| 症状 | 更可能的层次 | 重点检查 |
| --- | --- | --- |
| SQL 长时间没有产生扫描任务 | 规划阶段 | Catalog 延迟、Metadata JSON、Manifest 数量和元数据缓存 |
| 任务很多但每个任务读取很少 | 文件布局 | 小文件数量、目标文件大小、碎分区 |
| 读取字节远超结果数据 | 数据裁剪 | 分区策略、列统计、排序与过滤条件是否匹配 |
| Delete File 合并占比高 | 行级变更 | Merge-on-Read 的删除文件数量与后台重写周期 |

## 📄 提交时

```text
1. Writer 读取当前元数据 M0 和基础快照 S0
2. Writer 写出新的 Data File 或 Delete File
3. Writer 生成 Manifest、Snapshot S1 和元数据 M1
4. Writer 请求 Catalog 将入口从 M0 原子替换为 M1
5. 若入口已变化，则刷新状态、检查冲突并决定重试或失败
```

这是一种乐观并发控制。读者绑定提交前或提交后的某一个完整 Snapshot，提交过程中的临时文件组合不作为可读版本发布。

**乐观并发控制**的思路是：写入前不把整张表锁住，提交时才检查自己依赖的旧版本是否仍是当前版本。它“乐观”地假设冲突不常发生；发现冲突时再检查、重试或失败。

最后一步是带预期版本的条件更新：写入者声明自己基于 M0 生成 M1，Catalog 只在当前入口仍是 M0 时接受 M1。原子操作发生在“当前元数据入口从 M0 切换到 M1”这一步；Data File、Manifest 和 Metadata JSON 在入口切换前已经写入存储。

原子切换可以类比网站发布：新版本的所有文件先准备好，最后一次性把“当前版本”从旧目录改到新目录。准备阶段失败不会让用户进入未完成的新目录。

### 🔖 两个写者竞争

```text
Writer A：基于 M0 生成 M1 -> 提交成功，当前入口变为 M1
Writer B：基于 M0 生成 M2 -> 发现当前已不是 M0，提交被拒绝
Writer B：刷新到 M1 -> 检查冲突 -> 可安全重放时生成 M3 再提交
```

Catalog 的入口比较会阻止 Writer B 静默覆盖 Writer A。两个 `MERGE` 之间的业务语义冲突则由冲突检查、隔离级别、引擎实现和业务规则共同判定。Append、Overwrite、DELETE、MERGE 和数据压缩的冲突范围不同，重试策略需要按操作设定。

Append 向表追加数据；Overwrite 用新结果替换目标范围；`DELETE` 让匹配行失效；`MERGE` 按匹配结果组合更新、删除和插入。它们触碰现有数据的范围不同，因此需要分别配置冲突检查与重试策略。

这里要区分两件事：

- **元数据竞争**：B 基于过期的 M0 提交，Catalog 一定不能让它直接覆盖 A。
- **业务冲突**：A、B 是否修改了同一批逻辑数据，刷新后能否安全重放，要按操作和隔离规则判断。

业务版本号、事件顺序或来源优先级负责判断“两个来源谁才是正确订单状态”；Catalog 负责防止写者静默覆盖已经发布的新版本。

## 📄 隔离、重试与孤儿文件

Iceberg 的读取隔离依赖查询规划时选定的 Snapshot。写入隔离要结合操作和配置理解：可序列化隔离会检查并发新增文件是否也可能命中本次 `DELETE`/`UPDATE` 条件；较宽松的快照隔离可能只检查被删除或替换的文件是否冲突。

工程上需要注意：

- Append 通常更容易安全重试。
- Overwrite、DELETE、MERGE 和压缩必须验证被改写文件是否已变化。
- 为每种写入操作定义可重试条件，并单独校验并发业务语义。
- 提交最终失败时，已写出但未被有效 Snapshot 引用的文件可能成为孤儿文件。
- 通过 Iceberg 支持的过程管理表目录中的文件，保持元数据引用完整。
- 多引擎环境共享兼容的 Catalog 视图和当前表入口。

### 🔖 正确性范围

| 正确性需求 | 实现位置 |
| --- | --- |
| 单表元数据提交原子可见 | Iceberg Catalog 提交协议 |
| 查询绑定一个完整表版本 | Iceberg Snapshot |
| 基于旧版本提交时检测入口冲突 | Catalog 原子比较与 Iceberg 冲突检查 |
| 主键唯一性与业务变更顺序 | 上游去重、数据质量规则和业务版本号 |
| 跨表原子交付 | 上层协调机制或支持该语义的 Catalog |
| 长期保存与跨域灾备 | 备份、复制和恢复演练体系 |

## 📄 小结

- Catalog 给出 Metadata JSON 的入口，Snapshot 给出当前可见的文件集合。
- Metadata JSON 表示表级元数据版本，Snapshot 表示数据变更后的可见文件集合。
- 文件先写、入口后切换，读者看到的仍是完整 Snapshot。
- 提交冲突可能留下孤儿文件，由孤儿文件清理过程识别和删除。
- 慢查询要分开看规划、文件裁剪、文件布局和 Delete File 的成本。

## 📄 纸面推演

不用 Iceberg 环境也能验证模型。准备三张“文件卡”和两张“版本卡”：

```text
文件卡：A、B、C
版本卡：S0=[A,B]，S1=[A,B,C]
```

依次回答：

1. 查询 S0 会不会读 C？
2. 删除 C 的存储对象后，S1 还能否完整读取？
3. S0 过期后，A、B 一定可以删除吗？
4. Writer A 已把当前入口从 M0 改成 M1，Writer B 还能否直接发布基于 M0 的 M2？

<details>
<summary>参考答案</summary>

1. 不会，Snapshot 的引用集合决定可见文件。
2. 不能，元数据引用了不存在的文件，所以禁止手工删除被引用文件。
3. 不一定，S1 仍引用 A、B；文件是否可删取决于是否仍被任何有效引用使用。
4. 不能，B 必须刷新并经过冲突检查，再决定重试或失败。

</details>
