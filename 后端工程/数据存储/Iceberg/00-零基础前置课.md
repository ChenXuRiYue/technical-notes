# 📌 学 Iceberg 前，先看懂数据系统

如果你只接触过 MySQL，可以先把 Iceberg 理解为：**给一大批数据文件增加“表的目录、版本和安全换版规则”**。

本篇从一张普通业务表出发，逐步建立后文需要的数据系统概念。只要理解表、行、列和基本 SQL，就可以开始。

## 📄 从一张订单表开始

下面是一张表。表由列和行组成：

| order_id | user_id | amount | created_at |
| --- | --- | --- | --- |
| 1001 | 7 | 99.00 | 2026-08-01 10:00:00 |
| 1002 | 8 | 35.00 | 2026-08-01 10:01:00 |

- **行（row）**：一个业务对象的一条记录，例如订单 1001。
- **列（column）**：记录的一个属性，例如金额。
- **Schema**：这张表的结构说明书，规定列名、类型、是否允许为空等。
- **查询**：读取满足条件的数据，例如“统计昨天的销售额”。
- **写入**：增加、修改或删除数据。

分析 SQL 中还会反复出现三个动作：

- **过滤（filter）**：只保留满足条件的行，例如只看 8 月 1 日事件。
- **聚合（aggregate）**：把多行汇总成统计值，例如按城市计算订单数和总金额。
- **Join（连接）**：按关联条件把两张表的列拼起来，例如按 `user_id` 给订单补上用户所在城市。

在 MySQL 中，数据库替你管理数据页、索引、事务和表。使用者只看到一张逻辑表，很少关心数据究竟位于哪个文件。

但分析数据不断增长后，一个数据库不一定适合同时承担两类工作：

```text
业务请求：根据 order_id 查一笔订单，马上返回
分析请求：扫描一年订单，按城市和月份汇总
```

第一类只碰少量行，第二类可能读取几十亿行。它们对存储和计算的要求很不一样。

## 📄 OLTP 与 OLAP

| 类型 | 白话理解 | 常见操作 | 常见系统 |
| --- | --- | --- | --- |
| OLTP（联机事务处理） | 服务正在下单、付款、改地址的用户 | 高频小读写、点查、单行更新 | MySQL、PostgreSQL |
| OLAP（联机分析处理） | 从大量历史数据中统计趋势 | 大范围扫描、聚合、Join | Spark、Trino、分析数据库 |

Iceberg 主要服务 OLAP。它不提供 MySQL 那样的主键索引、唯一约束和毫秒级随机单行更新能力。

这里的 **事务** 是“若干变化作为一个完整结果出现”。例如转账中的扣款和入账需要同时成功。Iceberg 把一张表的一批文件作为完整版本发布：整批生效，或者继续使用旧版本。它的事务边界主要是一张表；跨表交易由数据库或上层协调机制处理。

## 📄 为什么分析数据会变成文件

设想每天从业务库导出一份订单：

```text
warehouse/orders/2026-08-01/orders-001.parquet
warehouse/orders/2026-08-01/orders-002.parquet
warehouse/orders/2026-08-02/orders-001.parquet
```

这样做有三个直接好处：

1. 存储可以独立扩容，不要求一台数据库服务器装下所有历史数据。
2. 多台计算机器可以各读一部分文件，并行完成统计。
3. 数据可以采用适合分析和压缩的列式文件格式。

随着文件增多，可靠的表还需要回答这些问题：

- 查询应该读取哪些文件，能否只靠目录名判断？
- 任务只成功写了一半时，读者会不会看到半批数据？
- 两个任务同时修改文件时，谁的结果有效？
- 列改名后，旧文件中的列如何对应到新名字？
- 昨天删错数据，怎样回到删除前？

Iceberg 就是在回答这些问题。

## 📄 存储、文件格式、表格式、计算引擎

先把四类东西分开。它们经常一起出现，但职责不同：

```text
Spark / Flink / Trino       计算：谁来执行任务
            |
         Iceberg            表格式：哪些文件构成哪一版表
            |
    Parquet / ORC / Avro    文件格式：一个文件内部怎样编码
            |
      S3 / OSS / HDFS       存储：文件字节放在哪里
```

可以用图书馆作类比：

| 数据系统 | 图书馆类比 |
| --- | --- |
| S3 / OSS / HDFS | 书库和书架，负责把书保存下来 |
| Parquet / ORC / Avro | 一本书内部的装订与排版格式 |
| Iceberg | 馆藏目录的版本，记录当前有哪些书及其分类 |
| Catalog | 服务台的目录入口，从书名找到当前馆藏目录 |
| Spark / Flink / Trino | 查书、整理书和做统计的工作人员 |

类比只用于记职责：真实的 Iceberg Catalog 还必须参与并发提交，Iceberg 元数据也不仅是文件名列表。

### 🔖 存储是什么

- **本地文件系统**：文件位于一台机器，例如 `/data/orders.parquet`。
- **HDFS**：把多台机器的磁盘组织成一个分布式文件系统，适合大文件的高吞吐读写。
- **对象存储**：S3、OSS 等服务把数据保存为对象，通常用 `s3://bucket/path/file` 一类 URI 访问。它使用对象接口和远程请求访问数据，操作语义与延迟不同于本地文件系统。

URI（统一资源标识符）是资源地址。`s3://lake/orders/a.parquet` 中，`s3` 是访问方式，`lake` 是存储桶，后面是对象键。

### 🔖 文件格式是什么

CSV、JSON 是人容易查看的文本格式；Parquet、ORC、Avro 是带 Schema 的二进制格式。

- Parquet、ORC 主要按列组织。同一列的值放得更近，分析查询可只读需要的列，也更容易压缩。
- Avro 主要按行组织，常用于整条记录的序列化与交换。

例如 `SELECT AVG(amount)` 只需要 `amount` 列。列式文件允许引擎尽量不读取 `user_id` 等无关列，这叫 **列裁剪**。

### 🔖 表格式是什么

表格式在许多 Parquet、ORC 或 Avro 数据文件之上规定：

- 当前表包含哪些文件；
- 列、分区和统计信息怎样描述；
- 一次新写入怎样原子发布；
- 历史版本怎样保留和读取。

Iceberg、Delta Lake、Apache Hudi 都属于开放表格式方案，但协议、生态和具体能力不同。本教程只讨论 Iceberg。

### 🔖 计算引擎是什么

计算引擎真正执行 SQL 和代码：读取文件、过滤、Join、聚合，再写出结果。

- **Spark**：擅长批量 ETL、历史回填和表维护。
- **Flink**：擅长持续到来的事件流和有状态计算。
- **Trino**：擅长交互式 SQL 和跨数据源查询。

Spark、Flink、Trino 等计算引擎启动计算资源并执行 `SELECT`；Iceberg 向它们提供表元数据和读写规则。

分布式引擎会把一次计算拆成许多 **Task（任务单元）**，交给不同的 **Worker（工作节点）** 并行执行。**并行度**表示同一阶段能有多少任务同时工作。并行度太低可能用不满资源，太高又可能写出大量小文件。

## 📄 数据仓库、数据湖与湖仓

这些名称描述数据平台如何组织存储、计算和治理：

| 名称 | 先抓住的特点 | 常见取舍 |
| --- | --- | --- |
| 数据仓库 | 先按治理好的表结构装入数据，再面向报表和分析 | 表管理和查询体验强，存储/计算常与产品绑定 |
| 数据湖 | 在低成本存储中保留大量原始和加工数据 | 开放灵活，但裸文件容易出现一致性和治理问题 |
| 湖仓（Lakehouse） | 在数据湖存储上补充表、事务和治理能力 | 保留开放存储，同时获得更接近仓库的表体验 |

Iceberg 为湖仓提供开放表格式。完整生产平台还会组合计算引擎、Catalog、权限、调度、监控和数据质量系统。

## 📄 批处理、流处理、ETL 与 CDC

### 🔖 有界批次与无界数据流

- **批处理**：输入有明确起点和终点，例如“处理昨天全部订单”。
- **流处理**：数据持续到达，理论上没有终点，例如“每来一笔支付就更新实时指标”。

“批流一体”让批任务和流任务按兼容语义读写同一套表。Spark 和 Flink 可以继续采用各自的执行模型。

持续运行的流任务会定期做 **Checkpoint（检查点）**：把消费位置和计算状态保存下来，故障后从一致位置恢复。Checkpoint 保证流任务自身的恢复进度；Iceberg Snapshot 表示一次表提交后的可见文件集合，两者处在不同系统中，需要由 Flink Connector 协作提交。

Connector（连接器）是计算引擎对接外部系统的适配组件，例如 Flink Iceberg Connector 知道怎样把 Flink 的记录与 Checkpoint 生命周期转换为 Iceberg 写入和提交。

### 🔖 ETL

ETL 是 Extract、Transform、Load：

```text
从业务库提取订单 -> 清洗金额和时间 -> 写入分析表
```

有些平台按 Extract、Load、Transform 的顺序工作，称为 ELT。两者的核心都是把源数据加工成可分析的数据。

### 🔖 CDC

CDC（Change Data Capture，变更数据捕获）把业务库的插入、更新、删除变成一串变更事件。例如：

```text
订单 1001：amount 从 99 改为 89
```

Flink 等工具可以持续消费这些事件并写入 Iceberg。CDC 处理上游变化的捕获，`MERGE`/Delete File 处理变化在目标表中的表达。

## 📄 Catalog、Namespace 与 Warehouse

假设完整表名是：

```text
prod.analytics.user_events
```

- **Catalog `prod`**：表目录的入口。它把逻辑表名定位到当前 Iceberg 元数据，并协调安全提交。
- **Namespace `analytics`**：表的逻辑分组，作用近似数据库中的库或 Schema。不同引擎的叫法会有差异。
- **Table `user_events`**：表名。
- **Warehouse**：存放 Iceberg 表元数据和数据文件的根位置，例如 `s3://company-lake/warehouse/`。SQL 仍由计算引擎执行；这里的 Warehouse 专指文件根位置。

把三者串起来：

```text
逻辑名称 prod.analytics.user_events
             |
             v
Catalog 找到当前 metadata.json
             |
             v
metadata.json 再找到 Warehouse 中的清单和数据文件
```

## 📄 第一次认识 Snapshot

假设表最初只有两个文件：

```text
Snapshot S0 = [A.parquet, B.parquet]
```

今天追加了 `C.parquet`。Iceberg 保留 A、B，并发布一个引用 C 的新版本：

```text
Snapshot S1 = [A.parquet, B.parquet, C.parquet]
```

读取 S0 得到旧表，读取 S1 得到新表。Snapshot（快照）保存某个时刻表所引用文件集合的版本视图，各 Snapshot 可以复用未变化的文件。

这带来三个能力：

1. 提交 S1 前，读者继续完整读取 S0。
2. S1 发布后，新读者完整读取 S1，不会看到“只写了一半”的中间状态。
3. S0 尚未过期时，可以查询或恢复到旧版本。

## 📄 后文常见的写入词

| 术语 | 含义 |
| --- | --- |
| Append（追加） | 保留原数据，在表中增加新记录或新文件 |
| Overwrite（覆盖） | 用新结果替换满足范围或条件的旧数据视图 |
| Update（更新） | 让已有逻辑行呈现新值 |
| Delete（删除） | 让已有逻辑行不再可见 |
| Merge / Upsert | 按匹配条件组合更新、删除和插入；Upsert 特指存在则更新、不存在则插入 |

Iceberg 通常通过新的 Data File 或 Delete File 实现这些表层语义，再发布新 Snapshot。Parquet 数据文件一般按不可变文件处理。

## 📄 容量单位

教程中的 `MiB`、`GiB`、`TiB` 按 1024 进位，例如 `512 MiB = 512 × 1024 × 1024` 字节；`MB`、`GB`、`TB` 按 1000 进位。工程交流中两套单位有时会被口头混用，配置时以实际字节值为准。`PB` 是比 `TB` 更大的十进制容量单位，`1 PB = 1000 TB`。

## 📄 用一句话说清 Iceberg

先遮住下面答案，试着向一个只会 MySQL 的同事解释 Iceberg。

> Iceberg 用带版本的元数据记录哪些数据文件组成一张表，并规定多次读写如何安全地看到完整版本。存储系统保存文件字节，计算引擎执行 SQL。

检查解释中是否说清 Iceberg 管理的对象和文件集合换版过程。只出现“数据湖、ACID、湖仓”等术语时，回到“文件集合如何换版”这一层补学。

## 📄 学前自测

先合上正文，用自己的话回答“为什么”：

1. 一批 Parquet 文件要成为可靠的表，还需要哪些能力？
2. Iceberg 与 Spark 各自承担什么职责？
3. Iceberg 与 MySQL 分别适合处理什么负载？
4. `prod.analytics.user_events` 的三段分别可能表示什么？
5. 新 Snapshot 是否一定复制全部旧数据文件？

<details>
<summary>参考答案</summary>

1. 文件本身不统一规定当前有效集合、并发提交、历史版本和 Schema/分区演进。
2. Iceberg 是表格式和读写协议，不提供执行 SQL 所需的计算资源与调度。
3. Iceberg 面向大规模分析，不提供 OLTP 数据库的主键索引、高频随机单行事务和强约束能力。
4. 通常是 Catalog、Namespace、Table；具体名称解析以引擎配置为准。
5. 不一定。新旧 Snapshot 可以复用未变化的数据文件和部分元数据。

</details>
