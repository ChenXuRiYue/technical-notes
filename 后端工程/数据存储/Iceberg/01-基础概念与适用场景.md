# 📌 Iceberg 基础概念与适用场景

Apache Iceberg 是一种开放表格式。它把分散在对象存储或 HDFS 上的数据文件组织成一张具有 Schema、分区、快照和原子提交语义的表。

> 前置要求：先完成 [零基础前置课](00-零基础前置课.md)，能够区分存储、文件格式、表格式和计算引擎。

## 📄 这一篇要解决什么问题

假设每天有一个任务把 `user_events` 写成 Parquet：

```text
events/2026-08-01/part-001.parquet
events/2026-08-02/part-001.parquet
```

第三天的任务写出两个文件后失败了一个；第四天有人修正历史数据，又留下了新旧两份文件。此时“把目录下所有 Parquet 都读进来”已经无法回答：哪一批提交是完整的、哪份修正有效、哪些是失败任务的残留。

**Iceberg 给文件集合建立唯一、可版本化的事实来源。** 查询性能还会受到文件格式、数据布局和计算引擎的共同影响。

学完后，你应该能不用“湖仓”这个词，回答：

1. Iceberg 究竟管理什么？
2. 一堆 Parquet 为什么不自然等于一张表？
3. Iceberg 与 MySQL、Spark、S3 的边界在哪里？
4. 什么场景引入 Iceberg 反而更复杂？

## 📄 先用普通语言解释

把当前表想成一张经过发布的文件清单：

```text
版本 S0：[A.parquet, B.parquet]
版本 S1：[A.parquet, B.parquet, C.parquet]
```

查询 S1 时，引擎读取清单中的 A、B、C。目录里失败任务写下的 D 没有被 S1 引用，因此不会进入查询。新版本发布的最后一步是**原子操作**：对外只呈现发布前或发布后的完整状态。

正式说法是：Snapshot 记录一次提交后可见的文件集合，Catalog 提供当前表元数据的权威入口。后文会逐层展开它们的文件结构。

## 📄 一张 Iceberg 表如何工作

Iceberg 为一张表维护明确的元数据入口和版本链。Catalog 定位当前 Metadata JSON，Metadata JSON 记录 Schema、分区、排序和 Snapshot，Snapshot 再经由 Manifest 定位当前有效的 Data File 和 Delete File。

核心读写规则可以概括为三点：

1. **读什么？** 读当前或查询指定 Snapshot 记录的文件集合。
2. **怎么写？** 先写新数据和元数据，最后原子替换表的当前元数据入口。
3. **如何演进？** 新规则用于后续写入，读取时用字段 ID 解释历史列，并按各 Data File 所属的 Partition Spec 裁剪文件。

这里的 **演进（evolution）** 让新旧规则同时存在并被正确解释。新规则用于后续写入，历史数据通过专门的数据重写获得新布局。字段 ID 是列的稳定编号；Partition Spec 是分区规则的版本化说明，都会在后续专题具体解释。

## 📄 Iceberg 在系统中的位置

```text
应用 / SQL 作业
        |
        v
查询引擎：执行 SQL、计算和调度
        |
        v
Iceberg：保存表的快照、文件集合和提交规则
        |-------------------|
        v                   v
Catalog：定位表入口     元数据 + 数据文件
                            |
                            v
                      S3 / OSS / HDFS
```

Iceberg 作为表格式与读写库集成在计算引擎中。Spark、Flink、Trino 执行计算，S3、OSS、HDFS 保存字节，Parquet、ORC、Avro 规定单个文件的编码，Iceberg 维护这些文件对应的表结构和版本。

Iceberg 的事务语义以单表 Snapshot 的原子提交和读写隔离为主：一次提交的文件集合要么整体可见，要么继续使用上一个完整 Snapshot。跨表原子性、主键唯一性和行级锁由其他系统或上层业务机制提供。

Iceberg 保证一批表变化作为完整版本发布。业务规则由相应的数据链路继续保证，例如上游去重或数据质量检查负责控制 `event_id` 重复。

## 📄 五层结构

| 层次 | 在 Iceberg 链路中的作用 |
| --- | --- |
| 存储：S3 / OSS / HDFS | 持久保存元数据文件和数据文件的字节 |
| 文件格式：[Parquet / ORC / Avro](../数据文件格式/Parquet、ORC 与 Avro.md) | 定义单个数据文件的组织、编码、压缩和读取方式 |
| 表格式：Iceberg | 定义表的文件集合、Schema、分区、Snapshot 和提交规则 |
| Catalog | 用表名定位当前 Metadata JSON，并协调新版本的原子提交 |
| 查询引擎：[Spark](../../数据处理/Spark.md) / [Flink](../../数据处理/Flink.md) / [Trino](../../数据处理/Trino.md) | 解析 SQL、规划文件扫描，并执行读取、写入、聚合和 Join |

## 📄 计算引擎的分工

三个引擎的完整教程位于 [数据处理与查询引擎](../../数据处理/README.md)。在 Iceberg 链路中，它们通常这样分工：

| 引擎 | 典型职责 | 更适合的负载 |
| --- | --- | --- |
| Spark | 批量 ETL、历史回填、`MERGE INTO`、小文件合并和表维护 | 有界批处理、较重的数据改写 |
| Flink | CDC/事件流清洗、实时聚合、持续写入和 Checkpoint 协作 | 无界流、低延迟持续处理 |
| Trino | 交互式 SQL、BI 报表、跨 Catalog 联邦查询 | 低等待的即席分析 |

BI（Business Intelligence，商业智能）是面向报表、指标和经营分析的一类应用。联邦查询通过 Connector 在一条查询中访问多个独立数据源，省去预先集中复制全部数据的步骤。Checkpoint 和 Connector 已在 [零基础前置课](00-零基础前置课.md) 中说明。

```text
数据字节：S3 / OSS / HDFS
表的结构与版本：Iceberg
批处理与维护：Spark
持续流处理：Flink
交互式 SQL：Trino
```

引擎组合由负载类型决定：离线 ETL 可单独使用 Spark，交互式查询可使用 Trino，持续事件处理则引入 Flink。多引擎读写同一张表时，它们需要共享同一 Catalog 视图并兼容表格式版本。

## 📄 适用范围

### 🔖 适合

- 数据主体位于对象存储或 HDFS，规模已达到 TB/PB 级。
- Spark、Flink、Trino 等多个引擎需要读写同一份数据。
- 需要快照隔离、时间旅行、回滚或基于快照的增量扫描。
- 表结构、分区策略会持续演进，不希望每次变更都重写整表。
- 希望数据与计算引擎解耦，避免绑定某个引擎的私有存储格式。

### 🔖 更适合其他系统的场景

- 毫秒级点查、高频单行更新和主键约束，优先评估 MySQL、PostgreSQL、HBase 等系统。
- 少量数据与单一批处理任务，可直接管理 Parquet 文件。
- 跨表强事务需要事务数据库或上层交易协调机制。
- 生产接入 Iceberg 同时需要小文件合并、Snapshot 过期、监控和兼容升级能力。

### 🔖 引入前看这几项

| 观察点 | 适合引入 | 可采用的简化方案 |
| --- | --- | --- |
| 数据规模 | 文件数和扫描成本已经明显影响任务 | 少量数据由单库或单任务即可管理 |
| 引擎数量 | 多引擎必须共享一致的表视图 | 只有一个简单离线脚本 |
| 变更模式 | Append 为主，批量更新可维护 | 高频随机单行更新 |
| 运维能力 | 能建立压缩、保留、监控和恢复流程 | 无人负责表维护与兼容升级 |
| 一致性边界 | 单表快照满足业务要求 | 依赖跨表原子提交和强约束 |

### 🔖 做一次反向判断

下面三个团队中，谁最需要 Iceberg？先回答，再展开参考解释。

1. 10 GB 数据，每晚一个 Python 脚本覆盖一个 Parquet 文件。
2. 500 TB 事件数据，由 Flink 持续写入，Spark 回填，Trino 查询，并需要保留七天历史版本。
3. 订单支付接口需要按主键在 10 ms 内更新一行，并保证余额表与流水表同时提交。

## 📄 非结构化资产

Iceberg 直接管理的 Data File 使用 Parquet、ORC 或 Avro。MP4、JPEG、MCAP、PCD、MDF4 等领域文件作为原始资产存放在 OSS/S3/HDFS，另建 Iceberg 表记录它们的 URI、时间范围、传感器、校验值、标签和版本。

```text
原始资产层（OSS/S3/HDFS）
└── MP4 / MCAP / PCD / MDF4 / JSON ...
                |
                | URI、时间范围、传感器、校验值、版本
                v
Iceberg 索引与派生数据层
├── sensor_asset：原始文件索引
├── scenario_event：场景挖掘结果
├── annotation：标注与标签版本
└── dataset_item：训练数据集成员
```

Iceberg 表提供按时间、传感器、场景、标签和数据集版本查找资产的结构化索引。MP4 帧定位、PCD 点云解码等文件内部处理由专用编解码库和数据处理作业完成。

## 📄 小结

- 存储保存字节，Parquet/ORC/Avro 规定单个文件的编码，Iceberg 记录一张表的文件集合，计算引擎执行查询。
- 读表时从 Catalog 进入当前 Metadata JSON，再选定 Snapshot 及其文件集合。
- Iceberg 的原子提交边界通常是一张表，跨表原子性需要额外协调机制。
- 是否引入 Iceberg，要看数据规模、引擎数量、变更模式和维护能力。
