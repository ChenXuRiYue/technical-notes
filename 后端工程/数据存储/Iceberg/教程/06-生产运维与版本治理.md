# 📌 Iceberg 生产运维与版本治理

Iceberg 生产运维围绕四类对象展开：Data File 的大小与数量、Delete File 的读时合并成本、Snapshot 的保留窗口，以及表格式与读写引擎的版本兼容性。

## 📄 这一篇要解决什么问题

Iceberg 按表协议保证提交正确。理想的数据布局由写入参数和持续维护共同形成。假设 Flink 每分钟提交一批很小的文件，`MERGE` 又不断产生 Delete File：表仍然能查，但每次规划要处理更多清单，执行任务要打开更多小文件，查询还要合并删除记录。与此同时，旧 Snapshot 会继续保护历史文件，存储用量不断增长。

Iceberg 运维通过下面的反馈环持续调整表状态：

```text
观察指标 -> 判断成本来自哪一层 -> 只做对应维护
    ^                                  |
    |                                  v
    +----------- 比较维护前后结果 <----+
```

学完后，你应该能解释每个维护过程的作用对象与边界，以及为什么执行顺序和保留窗口关系到数据安全。

## 📄 先看懂四类成本

| 对象 | 过多时为什么慢 | 对应动作 |
| --- | --- | --- |
| 小 Data File | 每个文件都有打开、请求、调度和元数据成本 | 重写数据文件，并调整上游写入批次 |
| Delete File | 读取时要把删除表达与数据合并 | 重写受影响数据/删除文件 |
| Manifest | 查询规划要读取和筛选更多清单 | 在规划确为瓶颈时重写 Manifest |
| Snapshot | 历史引用保护更多文件和元数据 | 按业务窗口过期旧 Snapshot |

小文件没有一个脱离环境的固定字节阈值。“小”表示相对于目标文件大小、对象存储开销和查询并行度，文件小到管理成本明显侵蚀有效扫描吞吐。

## 📄 维护前先看指标

生产上按表记录：

- 每次提交新增的 Data File、Delete File 和 Manifest 数量。
- 数据文件大小的 P50/P95，以及远低于目标大小的文件占比。
- Snapshot 数、最旧 Snapshot 时间、Metadata JSON 大小。
- 查询规划耗时、扫描文件数和实际读取字节数。
- 提交耗时、冲突率、重试次数和失败率。

P50/P95 是文件大小分布的第 50/95 百分位，比平均值更容易暴露“大量小文件夹着少数大文件”的问题。小文件的成本包括元数据膨胀、对象存储请求、任务调度和打开文件开销。

如果 100 个文件中有 95 个不大于 20 MiB，则 P95 约为 20 MiB。若另有 5 个超大文件，平均值可能被它们拉高，掩盖“大多数文件很小”；分位数能更直接描述分布。

### 🔖 指标与维护动作

| 观察到的信号 | 可能的问题 | 优先动作 |
| --- | --- | --- |
| 文件数快速增长，平均文件小 | 写入并行度过高或 CDC 批次过小 | 调整写入批次和目标文件大小，再重写活跃分区 |
| 规划耗时升高，扫描字节未变 | Manifest 过多或 Catalog/对象存储延迟 | 检查 Manifest，必要时重写 Manifest |
| Delete File 数量和读取放大升高 | Merge-on-Read 累积 | 合并删除文件和受影响 Data File |
| 最老 Snapshot 超出业务窗口 | 过期任务停摆或长期 Branch/Tag 引用 | 检查引用、恢复维护任务并重新评估保留策略 |

## 📄 合并小文件

```sql
CALL prod.system.rewrite_data_files(
    table => 'analytics.user_events',
    options => map(
        'target-file-size-bytes', '536870912',
        'min-input-files', '5'
    )
);
```

重写范围优先选择最近且仍活跃的分区。执行周期由小文件产生速度和查询性能目标驱动。重写前后记录文件数、P50/P95 文件大小、规划耗时和扫描字节，确认维护改善了目标指标。

`rewrite_data_files` 会把选定范围的数据重新写成数量更少、布局更合适的新 Data File，并提交新 Snapshot。随后还要调整上游写入批次和并行度，控制新小文件的产生速度。

## 📄 过期旧快照

```sql
CALL prod.system.expire_snapshots(
    table => 'analytics.user_events',
    older_than => TIMESTAMP '2026-07-28 00:00:00',
    retain_last => 20,
    stream_results => true
);
```

保留周期必须长于：

- 业务承诺的回滚和时间旅行窗口。
- 下游增量任务可能停顿的最长时间。
- 审计、复现和灾备流程需要的历史周期。

Branch 或 Tag 引用会保护相应 Snapshot 及其文件，因此保留策略还要监控长期存活的命名引用。时间旅行提供表内版本访问；跨域复制、备份和灾备演练构成独立的长期恢复体系。

保留窗口可以用两个灾备术语辅助思考：RPO（恢复点目标）表示最多能接受丢失多新的数据，RTO（恢复时间目标）表示故障后最多允许多久恢复。Catalog 备份、跨域文件复制、Iceberg Snapshot 和恢复流程共同支撑这些目标。

过期 Snapshot 从 Iceberg 可达的快照历史出发，按保留策略移除旧 Snapshot 及仅由它们引用的文件。孤儿清理从存储侧查找未被有效元数据引用的文件。两项维护各自处理不同对象。

## 📄 清理孤儿文件

```sql
-- 先只列出候选文件
CALL prod.system.remove_orphan_files(
    table => 'analytics.user_events',
    older_than => TIMESTAMP '2026-07-31 00:00:00',
    dry_run => true
);
```

核对 dry run 结果后再执行真实删除。将 `older_than` 设在所有运行中写入任务的开始时间之前，并覆盖最长写入时长和额外安全余量。保留窗口过短时，仍在写入的未提交文件可能被误判为孤儿。

Dry run（试运行）列出按当前条件将被处理的候选对象，供人工和自动校验流程复核范围。真实删除仍要保留操作审计和恢复手段。

如果更换过存储 URI 的 scheme 或 authority，必须先处理路径等价性，否则同一文件可能因字符串路径不同而被误判为孤儿。

## 📄 重写 Manifest

```sql
CALL prod.system.rewrite_manifests(
    table => 'analytics.user_events'
);
```

Manifest 重写的触发条件是 Manifest 数量较多，或写入布局与主要查询过滤条件不对齐，并且查询规划已经成为瓶颈。执行后同时复查 Manifest 数量和规划耗时。

重写 Manifest 优化文件清单的组织，主要改善查询规划阶段。小 Parquet 由 `rewrite_data_files` 合并，业务数据扫描量则由分区、排序、统计裁剪和查询条件共同决定。

## 📄 安全顺序

```text
1. 用元数据表和查询指标确认问题
2. 按需合并 Data File / Delete File / Manifest
3. 按业务保留策略过期 Snapshot
4. 孤儿文件先 dry run、复核，再执行删除
5. 记录维护前后指标和操作审计
```

为什么先重写、后过期、最后查孤儿：重写会产生新 Snapshot 和新文件；过期旧 Snapshot 后，旧布局中仅由历史版本引用的文件才可能失去引用；孤儿清理则从存储侧寻找最终无引用的文件。实际任务不必每次全部执行，但删除动作必须建立在已确认的引用与时间窗口上。

## 📄 表格式版本治理

- **v1**：提供 Snapshot、Schema/Partition 演进和 Append/Overwrite 等基础表能力。
- **v2**：在 v1 基础上增加 Delete File 和行级更新语义，是当前多引擎生产互操作的实用起点。
- **v3 及以后**：规范可能增加 Deletion Vector、Row Lineage 等扩展能力。版本状态和实现支持会持续变化，不在静态教程中固定结论；升级时查询当前规范，并验证所有生产读写引擎、Catalog 和工具链。

版本成熟度分为三层：表格式规范定稿、Iceberg 语言库实现、计算引擎与 Connector 稳定读写。生产选型以整条链路中最弱组件的能力为上限。

表格式版本和 Iceberg 依赖包版本是两个独立维度：前者是表级存储协议，后者是具体读写实现的发布版本。升级前建立兼容矩阵：

Deletion Vector 是“某个数据文件的哪些行位置已删除”的紧凑位图表示；Row Lineage 是追踪一行在插入和更新过程中的稳定身份与先后关系。启用这些特性前，验证所有写入者和读取者都能正确解释它们。

| 组件 | 版本 | 可读格式版本 | 可写格式版本 | DELETE/MERGE | Branch/Tag | 维护过程 |
| --- | --- | --- | --- | --- | --- | --- |
| Spark | | | | | | |
| Flink | | | | | | |
| Trino/Presto | | | | | | |
| Catalog | | | | | | |

升级流程：

1. 填写所有读写引擎、Connector、Catalog 和维护工具的版本。
2. 在隔离表验证读、写、`MERGE`、时间旅行、回滚和维护过程。
3. 先升级客户端并观察，再改变表格式版本。
4. 为回滚保留旧客户端、旧 Snapshot 和明确的恢复窗口。

## 📄 风险操作与处理

| 错误 | 后果 | 改法 |
| --- | --- | --- |
| 把 Iceberg 当成计算引擎 | 只建表，没有查询资源和调度方案 | 分开评估表格式、Catalog、引擎和存储 |
| 沿用 Hive 过细分区 | 小文件和元数据膨胀 | 从主要查询条件出发，用隐藏变换和统计裁剪 |
| 只看数据总量 | 100 GB 也可能因几十万小文件而很慢 | 同时看文件数、大小分布、Manifest 和规划时间 |
| 将时间旅行当永久备份 | Snapshot 过期或存储故障后无法恢复 | 另建备份和跨域复制，并进行恢复演练 |
| 不做保留策略就过期 Snapshot | 下游增量断点丢失，无法回滚 | 把 RPO、RTO、最长停顿和审计需求写成表级策略 |
| 直接执行孤儿文件删除 | 误删进行中的写入文件 | 先 dry run，保留时间大于最长任务时间并留余量 |
| 不检查多引擎兼容就升格式版本 | 部分引擎无法读表或语义不一致 | 隔离表验证完整读写链路后再升级 |
| 多引擎连接不同 Catalog 后端却当作同一张表 | 看见不同 Snapshot、入口不一致，甚至产生两套同名表 | 统一后端、Warehouse、Namespace 映射和权限配置 |
| 不确认语义就执行 `DROP/PURGE` | 只想取消注册却删掉数据，或误以为数据已清理 | 在目标引擎和 Catalog 上验证删除语义并保留恢复手段 |

## 📄 小结

- 一张表的维护顺序通常是：观察指标，按需重写文件，过期 Snapshot，最后清理孤儿文件。
- P50/P95 比平均值更容易暴露小文件问题。
- 依赖包版本和表格式版本是两套版本，兼容矩阵要分别记录。
- 生产删除和升级前，必须确认写入任务窗口、快照引用、权限和恢复路径。

## 📄 费曼诊断

先不看上面的动作表，判断下面问题应该查什么：

1. SQL 提交后 30 秒才开始产生 Task，但真正扫描很快。
2. Task 数量巨大，每个 Task 只读少量字节。
3. 扫描文件不多，但每次查询都花大量时间合并删除。
4. 存储持续增长，最旧 Snapshot 已远超承诺的回滚窗口。

参考方向依次是：规划层的 Catalog/Manifest；小 Data File；Delete File；Snapshot 保留和 Branch/Tag 引用。答完后再说明每个动作的作用对象和边界，检验故障定位是否准确。
