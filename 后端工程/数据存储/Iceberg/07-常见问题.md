## 📄 Q&A

**Q1：Iceberg 是“开放表格式”，到底开放了什么，又规定了什么？**

“开放”指表格式规范公开，Spark、Flink、Trino 等引擎可以按同一规范读写表，从而实现跨引擎互操作。表数据的访问仍由 Catalog 权限、对象存储权限和组织治理规则控制。

“表格式”规定一批数据文件如何组成一张表，包括文件集合、Schema、分区、Snapshot、统计信息和原子提交规则。单个数据文件的编码和压缩由 Parquet、ORC 或 Avro 文件格式定义。

可以这样区分：Parquet 管一个文件怎么存，Iceberg 管整张表的文件怎么组织和变更。

---

**Q2：Parquet、ORC 和 Avro 是什么，有什么区别？**

它们都是基于 Schema 的二进制数据文件格式，定义单个文件内部的数据组织、编码、压缩和读取方式。Iceberg 元数据再把多个这类文件组织成一张表。

假设数据有 `id`、`name`、`age` 三列，可以先做如下简化理解：

```text
Avro 按行组织：
[1, 张三, 20] [2, 李四, 30] [3, 王五, 40]

Parquet / ORC 按列组织：
id:   [1, 2, 3]
name: [张三, 李四, 王五]
age:  [20, 30, 40]
```

| 格式 | 组织方式 | 主要特点 | Iceberg 中的常见用途 |
| --- | --- | --- | --- |
| Parquet | 列式 | 只读查询需要的列，同类型数据压缩率高，广泛支持 Spark、Trino 等引擎 | 最常见的业务 Data File |
| ORC | 列式 | 与 Parquet 解决相似问题，在 Hive 生态中应用较多 | 业务 Data File |
| Avro | 行式 | 整行读写自然，适合序列化、传输和连续写入 | 可作为 Data File；Manifest List 和 Manifest 也使用 Avro 编码 |

详细结构与选择见 [Parquet、ORC 与 Avro](../数据文件格式/Parquet、ORC 与 Avro.md)。

列式文件在一个文件内按组织单位分块：Parquet 使用 Row Group，ORC 使用 Stripe，再在组内按列保存。因此 `SELECT AVG(age)` 可以主要读取 `age` 的列块，略过 `name` 的列块。

---

**Q3：HDFS 是什么，它与 Iceberg 是什么关系？**

HDFS 全称 Hadoop Distributed File System。它把多台服务器的磁盘组合成统一文件系统：大文件被拆成多个 Block，分散到不同机器并保存副本，以提供大容量存储和故障容错。

NameNode 管理目录、文件名和 Block 位置等元数据，DataNode 保存文件 Block。HDFS 的主要负载是大文件与高吞吐顺序读写；海量小文件会增加 NameNode 元数据和文件打开成本。

在 Iceberg 体系中，HDFS 负责保存 Data File 和元数据文件的字节，Iceberg 负责 Schema、Snapshot、文件集合和事务等表级语义：

```text
Iceberg：决定哪些文件组成当前的表
HDFS：保存这些文件的实际字节
```

S3 和 OSS 也位于底层存储位置。区别在于 HDFS 通常由团队自建并管理 NameNode/DataNode 集群，S3/OSS 则由云厂商提供对象存储服务。

---

**Q4：Schema、分区或排序变更后，Iceberg 如何仍然读懂旧文件？**

Schema、分区或排序演进先更新表元数据，新规则用于后续写入。历史文件保留原有布局，查询规划器按它们各自的规则版本解释和裁剪：

```text
旧文件 A：user_name，按 day(created_at) 分区，按 order_id 排序
新文件 B：buyer_name + region，按 month(created_at) 分区，按 created_at 排序
```

| 变化 | 典型例子 | 如何兼容旧文件 |
| --- | --- | --- |
| Schema 演进 | 增加列、重命名列、安全扩宽类型 | 用稳定字段 ID；新列在旧文件中读为 `null` |
| 分区演进 | `day(created_at)` 改为 `month(created_at)` | 保存多个 Partition Spec，规划时分别裁剪 |
| 排序演进 | `order_id` 改为 `created_at` | 旧文件保留旧布局，新文件使用新布局 |

将 `user_name` 重命名为 `buyer_name` 时，只要字段 ID 没变，旧文件中的原列仍会映射到当前 Schema。如果新增 `region`，旧文件没有这列，读取时得到 `null`，无需先重写旧文件。

---

**Q5：对象存储中的领域文件如何与 Iceberg 配合？**

S3、OSS 和 HDFS 保存原始领域文件与 Iceberg 文件。Iceberg Data File 使用 Parquet、ORC 或 Avro；MP4、JPEG、MCAP、PCD、MDF4 等原始文件由 Iceberg 表记录 URI 和结构化业务元数据：

```text
存储后端：S3 / OSS / HDFS
    可保存几乎任意字节

Iceberg Data File：Parquet / ORC / Avro
    Iceberg 可直接管理，计算引擎可按列裁剪并执行 SQL

领域原始文件：MP4 / JPEG / MCAP / PCD / MDF4 ...
    可放在存储中，由 Iceberg 表间接记录 URI 和业务元数据
```

例如 Iceberg 可以用 `sensor_asset` 表查出“上海雨天前视摄像头的所有视频 URI”。专用编解码库负责解析 MP4 和视频帧；Iceberg 对索引表中的结构化列提供统计与裁剪。

---

**Q6：Catalog 保存哪些内容？**

Catalog 保存或解析“表名 -> 当前 Metadata JSON”的入口，并管理 Namespace、表注册和 Catalog 级属性。表属性、Snapshot 历史、Manifest、Data File 和 Delete File 保存在 Warehouse 的对象存储或 HDFS 中。

```text
Catalog：告诉引擎从哪里进入
Metadata JSON：描述表当前版本和快照历史
Manifest：描述快照包含哪些数据文件
Data File：保存真正的业务记录
```

灾备同时覆盖 Catalog 状态与 Warehouse 文件：前者恢复表入口，后者恢复元数据和业务数据。恢复演练还要验证入口重新指向正确的 Metadata JSON。

---

**Q7：SQL 第一段 Catalog 与 Iceberg Catalog 如何对应？**

Spark 和 Trino 先用 SQL 第一段名称选择本引擎中的 Catalog 别名与插件配置，该配置再连接 REST、Hive、Glue、JDBC 等 Iceberg Catalog 后端。

```text
SQL Catalog 别名 -> 引擎插件/Connector -> Iceberg Catalog 后端 -> Metadata JSON
```

判断两个引擎是否访问同一张表，需要核对 Catalog 后端地址、Warehouse、Namespace 映射和认证配置。SQL 名称只是各引擎中的本地解析入口。

---

**Q8：Metadata JSON 版本和 Snapshot 分别表示什么？**

Metadata JSON 是表级元数据版本，包含 Schema、分区规则、表属性、Snapshot 历史和当前 Snapshot 引用。Snapshot 是某次数据变更提交后可见的文件集合。修改表属性、Schema 或 Branch/Tag 引用会产生新的 Metadata JSON；数据文件视图保持原样时，可以继续引用已有 Snapshot。

---

**Q9：时间旅行、回滚、Branch 和 Tag 有什么区别？**

时间旅行在查询时选择历史 Snapshot，当前表引用保持原值。回滚是一次新的元数据提交，把当前表引用指回历史 Snapshot。Branch 和 Tag 都是 Snapshot 的命名引用：Branch 可继续前进，Tag 通常固定不变，它们与 Snapshot 共享数据文件。独立灾备由跨域复制、备份和恢复演练提供。

---

**Q10：`event_id` 如何用于匹配，业务唯一性如何保证？**

Iceberg Schema 定义字段类型和 `NOT NULL` 等行结构约束。`MERGE INTO ... ON target.event_id = source.event_id` 规定本次计算如何匹配源表和目标表。业务唯一性由上游去重、质量校验、业务版本号或其他支持唯一约束的系统维护。

---

**Q11：Schema 删除列后，旧 Data File 如何清理？**

Schema 删除通常先改变表级元数据，旧 Data File 仍可能被历史 Snapshot、Branch 或 Tag 引用。普通逻辑删除可等待快照过期与文件清理；合规擦除需要重写受影响文件、处理所有有效引用，并验证备份和缓存。`ALTER TABLE DROP COLUMN` 只完成表级 Schema 变更。

---

**Q12：Iceberg 的 ACID 具体覆盖什么范围？**

ACID 是原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）的缩写。它是一组事务性质，不同系统的事务边界与约束能力不同。

Iceberg 的核心是单表 Snapshot 提交：一次文件集合变更完整发布或保持旧版本；查询绑定完整 Snapshot；提交通过 Catalog 做版本检查；已提交元数据和文件持久保存在存储中。

业务主键唯一由上游去重和质量规则维护，跨表转账由事务数据库或上层协调机制完成，行锁属于其他存储系统的并发控制方式。因此评估 ACID 时要继续明确事务边界、冲突检查范围和业务约束负责人。

---

**Q13：小文件、旧 Snapshot 和孤儿文件分别是什么问题？**

小文件是“被当前表有效引用，但数量太多、大小太小”的布局问题；旧 Snapshot 是“仍受历史版本引用”的保留问题；孤儿文件是“未被任何有效元数据引用”的残留问题。

因此：

- `rewrite_data_files` 改善当前数据布局；
- `expire_snapshots` 按策略移除旧版本引用；
- `remove_orphan_files` 查找存储侧的无引用文件，并且必须先 dry run。

三个动作分别处理数据布局、历史引用和无引用残留。

---

**Q14：Snapshot 怎样复用数据文件？**

Snapshot 描述某次提交后可见的文件集合。新旧 Snapshot 可以共同引用未变化的 Data File 和 Manifest：

```text
S0 = [A, B]
S1 = [A, B, C]
```

S1 复用 A、B，只新增对 C 的引用。也正因为文件会共享，判断一个历史 Snapshot 过期后能否删除某文件，必须看它是否仍被其他有效 Snapshot、Branch 或 Tag 引用。

---

**Q15：数据湖、湖仓与 Iceberg 是什么关系？**

数据湖强调在开放、可扩展的存储中保留大量原始和加工数据；湖仓在这类存储上补充可靠的表、事务与治理体验。Iceberg 提供其中的开放表格式层。完整平台继续组合存储、计算引擎、Catalog、权限、调度、质量和监控。

## 📄 排查时可以问

遇到查询、写入或维护问题时，可以依次问四件事：

1. 当前查询绑定的是哪个 Catalog 和 Snapshot？
2. 过滤条件能裁剪哪些分区、Manifest 和 Data File？
3. 变更是元数据演进，还是需要重写历史字节？
4. 维护或升级会影响哪个下游窗口、权限和恢复路径？
