# 📌 监控、备份与故障排查

审核服务报告“打开成片要 30 秒”。这句话还不能定位故障：慢点可能在路径查找、对象下载、本地缓存盘、应用读取模式，甚至只是某个客户端进程。排查要沿实际请求路径逐层收集证据。

学完本篇，你应该能把症状映射到 `status/stats/profile/info`，并能说明元数据备份、对象存储保护和恢复演练为何缺一不可。

## 📄 四个命令回答四种问题

| 命令 | 回答的问题 | 输入 |
| --- | --- | --- |
| `juicefs status` | 卷配置与哪些客户端会话活着？ | Meta URL |
| `juicefs stats` | 某个挂载点此刻哪一层繁忙？ | 挂载点 |
| `juicefs profile` | 哪类文件操作慢，由哪个进程发起？ | 挂载点或访问日志 |
| `juicefs info` | 某个路径怎样映射到 inode 与 Block？ | 路径或 inode |

常用形状：

```bash
juicefs status "redis://metadata.internal:6379/1"
juicefs stats /srv/media -l 1
juicefs profile /srv/media
juicefs info /srv/media/output/M1001-720p.mp4
```

Meta URL 可能包含认证信息。生产命令使用 Secret 文件或环境注入，并避免把口令写入工单和聊天记录。

## 📄 从用户症状向下排查

1. **固定请求**：记录客户端、路径、操作、开始时间、耗时、错误码和是否首次读取。
2. **比较范围**：同客户端其他路径、其他客户端同路径、同目录小文件和大文件是否都异常。
3. **看操作**：用 `profile` 判断慢在 `lookup/open/getattr/read/write/fsync` 哪一步。
4. **看资源层**：用 `stats` 对齐元数据、对象存储、缓存和缓冲指标。
5. **看对象**：用 `info` 检查单文件大小、Block 与碎片形状。
6. **看共享后端**：检查数据库延迟/错误、Bucket 请求错误/限流和网络。
7. **看客户端**：检查 JuiceFS 日志、FUSE、CPU、内存与缓存盘。

先收集同一时间窗的证据，再重启或调参。直接重启可能暂时清掉缓存和症状，也会丢失故障现场。

## 📄 症状到责任层

| 现象 | 第一检查点 | 再检查 |
| --- | --- | --- |
| 所有客户端 `ls` 都慢 | 元数据引擎 P99 与连接错误 | 目录规模、元数据缓存、网络 |
| `open` 快但冷读慢 | 对象存储 GET 延迟与吞吐 | 下载并发、readahead、网络 |
| 只有一台主机慢 | 本机缓存盘、CPU、FUSE、日志 | 挂载参数与版本差异 |
| 第二次读快很多 | 缓存命中 | 冷读基线和预热策略 |
| `fsync/close` 慢 | 上传带宽、缓冲拥塞、对象错误 | 小写模式与上传并发 |
| 路径存在但读取报 I/O 错误 | `info` 映射与对象可达性 | 凭据、生命周期误删、写回未上传 |
| 存储用量高于逻辑文件量 | 回收站、旧/碎片 Block、写回暂存 | 删除频率与维护状态 |

## 📄 生产监控最小集合

- FUSE 操作次数、错误率与延迟分位数。
- 元数据操作次数、延迟、错误和数据库自身容量/复制状态。
- 对象存储请求次数、流量、延迟、错误、限流和费用。
- 客户端内存缓冲、缓存命中、缓存盘使用率和 I/O 延迟。
- 活动会话、客户端版本、挂载点与心跳时间。
- 后台任务、回收站、待删除对象和自动备份最后成功时间。
- `--writeback` 场景的 staging Block 数、字节数和最老上传延迟。

后台挂载的默认日志路径因运行用户而异：root 常见为 `/var/log/juicefs.log`，普通用户常见为 `$HOME/.juicefs/juicefs.log`。生产配置日志轮转、集中采集和磁盘告警。

## 📄 为什么要备份两类东西

完整恢复依赖：

```text
元数据备份：恢复路径、inode、权限、Chunk/Slice/Block 映射
对象存储保护：恢复这些映射指向的 Block 字节
```

只恢复元数据但 Block 已被生命周期规则删除，路径存在却读不到内容。只保住 Bucket 但元数据丢失，也无法可靠重建原目录与文件偏移映射。

JuiceFS Community Edition 当前客户端默认定期把元数据备份到对象存储的 `meta/` 目录。官方文档同时说明：自动备份由客户端后台任务执行，默认周期与大规模文件数下的跳过策略会受版本和配置影响。生产必须监控“最后成功备份”，不能只确认开关存在。

数据库自身快照/备份与 `juicefs dump` 应共同使用。两者提供不同恢复速度、格式和一致性能力。

## 📄 手工导出边界

```bash
juicefs dump \
  "redis://metadata.internal:6379/1" \
  meta-dump-2026-08-27.json.gz
```

`dump` 生成跨元数据引擎可读取的备份格式，但对在线并发修改不提供快照一致性。需要严格一致的恢复点时，先停止或隔离写入，再执行受控导出；大规模卷还要评估导出对在线数据库 CPU、内存与延迟的影响。

默认导出会移除对象存储 Secret。恢复后通过受控凭据重新配置，避免用 `--keep-secret-key` 生成难以保护的明文密钥备份。

## 📄 在本地实验中做一次恢复演练

延续 [本地动手实验](02-本地动手实验.md)。先在源挂载仍可读时记录校验值，然后卸载以冻结写入：

```bash
export JFS_LAB_DIR=/absolute/path/to/juicefs-lab

cksum "$JFS_LAB_DIR/mount/review/M1001.txt" \
  > "$JFS_LAB_DIR/expected.cksum"

juicefs umount "$JFS_LAB_DIR/mount"

juicefs dump \
  "sqlite3://$JFS_LAB_DIR/metadata.db" \
  "$JFS_LAB_DIR/meta-dump.json.gz"
```

恢复到一个全新的空 SQLite 文件。这个本地 `file` 存储实验没有对象存储 Secret；使用 S3/OSS 等后端时，`dump` 默认不保留 Secret，`load` 后要先通过 `juicefs config` 安全补回凭据，再挂载验证：

```bash
mkdir -p "$JFS_LAB_DIR/restored-mount" "$JFS_LAB_DIR/restored-cache"

juicefs load \
  "sqlite3://$JFS_LAB_DIR/restored.db" \
  "$JFS_LAB_DIR/meta-dump.json.gz"

juicefs status "sqlite3://$JFS_LAB_DIR/restored.db"

juicefs mount -d \
  --cache-dir "$JFS_LAB_DIR/restored-cache" \
  "sqlite3://$JFS_LAB_DIR/restored.db" \
  "$JFS_LAB_DIR/restored-mount"

cksum "$JFS_LAB_DIR/restored-mount/review/M1001.txt"
cat "$JFS_LAB_DIR/expected.cksum"
```

两个校验值与字节数应该一致。恢复后的元数据仍指向原实验 `objects/`，所以这次演练同时验证了“恢复映射后能找到原 Block”。最后执行：

```bash
juicefs umount "$JFS_LAB_DIR/restored-mount"
```

生产演练要恢复到隔离数据库与隔离访问入口，避免恢复客户端和在线卷同时写同一数据集。

## 📄 检查与修复分开

JuiceFS 提供维护工具：

```bash
# 只检查泄漏对象，不删除
juicefs gc "redis://metadata.internal:6379/1"

# 检查文件系统一致性，不修复
juicefs fsck "redis://metadata.internal:6379/1"
```

`gc --delete` 会删除识别出的泄漏对象，`fsck --repair` 会修改状态，`destroy` 会销毁卷。它们属于高风险操作：先确认客户端版本、备份、业务写入窗口和官方操作说明，在隔离或审批流程中审阅检查结果，再决定是否执行。本教程不提供自动删除命令。

## 📄 RPO 与 RTO

- **RPO（恢复点目标）**：最多能接受丢失多新的元数据和文件，例如 15 分钟。
- **RTO（恢复时间目标）**：故障后最多允许多久恢复服务，例如 1 小时。

每小时一次备份无法自动满足 15 分钟 RPO；存在备份也不表示能在 1 小时内完成数据库恢复、凭据重配、挂载和校验。目标要通过备份周期、数据库复制、对象存储保护和定期恢复演练共同证明。

## 📄 先预测

元数据数据库完全丢失，但 Bucket 开启了跨区域复制，全部 Block 都还在。能否只把 Bucket 挂回来恢复目录？

不能直接恢复。对象键只保存内部 Block，缺少路径、inode、文件偏移与 Slice 映射。应恢复元数据引擎备份，再验证它指向的 Block 完整可读。

改变条件：元数据备份每小时成功，对象存储生命周期却会在 30 天后删除 `chunks/` 对象。恢复旧元数据只能得到指向已删除 Block 的映射。生命周期规则必须理解 JuiceFS 管理边界，不能绕过文件系统清理有效对象。

本教程没有在当前环境执行 JuiceFS 恢复实验；命令按 2026-08-27 官方文档核对。生产恢复前先在同版本隔离环境验证完整流程。
