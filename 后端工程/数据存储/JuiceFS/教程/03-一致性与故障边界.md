# 📌 一致性、并发与故障边界

转码服务正在写 `/output/M1001-720p.mp4`，审核服务同时尝试打开它。双方需要约定明确的观察点：哪个系统调用完成后，另一个客户端通过什么动作，应该看见哪个版本。

学完本篇，你应该能以 `write -> flush/fsync -> close -> reopen` 为时间轴解释可见性，并判断 `--writeback` 为什么会把本地缓存盘变成持久性风险的一部分。

## 📄 先定义四个观察时刻

| 时刻 | 已发生的事 | 可以声称什么 |
| --- | --- | --- |
| `write` 返回 | 字节已进入内核或客户端缓冲 | 写入调用被接受；不等于远端持久化完成 |
| `flush` 完成 | 当前待写 Slice 被推进上传与提交 | 本次缓冲错误有机会暴露；具体由调用链处理 |
| `fsync` 成功 | 应用显式要求同步持久化 | 当前客户端获得更强的完成证据 |
| `close` 成功 | 文件描述符关闭，默认写入完成 | 其他客户端重新 `open` 时应看见最新已提交状态 |

应用必须检查错误。忽略 `fsync` 或 `close` 的失败，再根据“前面的 `write` 返回成功”宣布业务完成，会丢失真正的持久化结果。

## 📄 默认 close-to-open 一致性

默认配置下，客户端 A 修改并关闭文件后，客户端 B 再次打开该文件时查询元数据服务，看到最新状态。这称为 **close-to-open consistency**。

```text
A: open -> write -> close 成功
                         |
                         v
B:                reopen -> 看见新状态
```

“重新打开”是关键观察点。客户端 B 如果一直持有旧文件描述符，或应用自己缓存内容，就不能只靠文件系统名称推断它立刻切换到了新版本。内核元数据缓存也有 TTL；当前官方默认挂载配置使用短 TTL，在性能与及时失效之间折中。

## 📄 用临时文件发布完整结果

媒体转码通常希望审核者看见完整成片，而不是边写边长大的正式文件。应用可以采用同目录临时文件加原子改名：

```text
1. 写 /output/.M1001-720p.mp4.job-42.tmp
2. 检查写入、fsync 与 close 结果
3. 校验大小、校验和或媒体格式
4. rename 到 /output/M1001-720p.mp4
```

`rename` 原子切换一个目录项，读者看到切换前名字指向的版本或切换后的版本。它不提供“视频、JSON、数据库任务状态三者一起提交”的跨系统事务。多个产物需要由清单文件、版本目录或上层任务状态协调。

## 📄 并发写与文件锁

元数据引擎记录文件锁和客户端会话，JuiceFS 支持常见 BSD flock 与 POSIX record lock。锁的用途是让协作应用约定谁可以修改某个文件范围。

锁不会自动修复没有遵守约定的业务程序。两个写者同时覆盖同一偏移时，系统会按实际提交顺序形成 Slice；最终字节可能混合两个写者的结果。媒体产物更稳妥的策略是：

- 每个任务写唯一临时路径。
- 只有获得业务发布权的任务执行最终 `rename`。
- 任务库用幂等键或状态条件防止两个任务同时发布同一版本。

## 📄 默认写入与 `--writeback`

默认模式使用“先上传、后提交”：

```text
内存缓冲 -> 上传 Block 到对象存储 -> 提交元数据 -> 对外可见
```

对象存储上传慢时，`close/fsync` 延迟会暴露出来，但元数据不会先指向尚未上传的 Block。

开启 `--writeback` 后，客户端把待上传数据放到本地缓存目录，先提交元数据，再异步上传：

```text
本地 rawstaging -> 提交元数据 -> 调用更快返回 -> 后台上传对象存储
```

这种模式适合短时间写入大量小文件且能够承担风险的场景。它改变了可靠性边界：上传完成前，本地 `rawstaging` 是唯一数据副本之一；磁盘损坏、目录被删或主机永久丢失可能造成无法恢复的数据缺口。其他节点读取尚未完成上传的 Block 也可能等待或报 I/O 错误。

因此，生产启用前必须回答：

1. 本地缓存盘是否独立、可靠并有容量监控？
2. 谁监控待上传 Block 数量和最老延迟？
3. 客户端退出或节点丢失时怎样告警和处置？
4. 业务是否允许已返回成功的数据仍依赖单机暂存？

答不清时保留默认写入顺序。

## 📄 元数据缓存也会改变观察点

JuiceFS 在内核和客户端进程中缓存元数据。默认禁用客户端 `--open-cache`，以维持 close-to-open 模型。为只读或读密集场景启用 `--open-cache` 后，在 TTL 过期前，另一个客户端的修改可能还不可见。

缓存参数不是纯性能数字。每次调大 `--attr-cache`、`--entry-cache`、`--dir-entry-cache` 或 `--open-cache`，都要同时写明：

- 哪类元数据被缓存；
- 最长允许多久看见旧状态；
- 读写客户端是否混用；
- 应用有没有版本目录或不可变文件名来规避覆盖可见性。

## 📄 故障矩阵

| 故障时刻 | 默认模式的结果 | 后续动作 |
| --- | --- | --- |
| Block 上传前客户端退出 | 元数据未提交，其他客户端不引用这批数据 | 应用重试，检查客户端日志 |
| Block 已上传、元数据提交失败 | 可能留下无引用对象 | 先确认写入终态，按官方 GC 检查流程处理 |
| 元数据引擎不可用 | 路径解析、权限和提交失败 | 恢复元数据服务，避免绕过它直接改 Bucket |
| 对象存储不可用 | 数据读写失败；已有元数据仍可能可查 | 检查网络、凭据、限流和服务状态 |
| `--writeback` 上传前缓存盘永久损坏 | 元数据可能已提交但 Block 丢失 | 触发数据完整性事件并从上游副本恢复 |
| 客户端 A 崩溃但共享后端正常 | 其他客户端仍可工作；会话由后台任务清理 | 查单机 FUSE、日志和缓存盘 |

## 📄 先预测

证据如下：

```text
上传服务：write 返回成功
上传服务：进程随后被 kill -9
审核服务：重新 open 后找不到完整文件
```

这是否违反 close-to-open 一致性？

不一定。`write` 成功只说明调用被接受；进程没有得到成功的 `fsync/close` 证据。close-to-open 的前提“写者完成关闭”没有成立。若答成“write 返回就已持久化”，回到本篇第一张表。

改变条件：`close` 成功，审核服务关闭旧描述符后重新打开仍长期看见旧内容。此时检查两端 JuiceFS 版本、挂载缓存参数、客户端日志与元数据服务，而不是先归咎对象存储内容。

## 📄 纸面推演

给三个时刻编号：

```text
T1: 写临时文件完成
T2: rename 到正式文件
T3: 写 review/M1001.json
```

在 T2 后、T3 前故障，审核者会看到成片但没有审核 JSON。这说明单次 `rename` 的原子边界只有一个目录项。请设计一个版本目录和 `manifest.json`：先把所有产物写入 `versions/job-42/`，最后原子发布一个只包含完整产物清单的入口文件。
