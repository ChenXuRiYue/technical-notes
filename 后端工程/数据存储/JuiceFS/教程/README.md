# 📌 JuiceFS：从共享目录到云原生分布式文件系统

基础谈资。JuiceFS 把对象存储提供的容量与数据库提供的元数据能力组合成一个共享文件系统。应用仍然可以使用目录、文件、权限、`open/read/write/rename` 等熟悉的接口，JuiceFS 客户端负责把这些操作翻译为元数据事务和对象存储请求。

本教程面向会使用 Linux 命令、理解基本后端服务和数据库，但没有分布式文件系统经验的工程师。学完后，你应该能从一次 `open("/srv/media/inbox/M1001.mp4")` 出发，追踪 FUSE、JuiceFS Client、元数据引擎、本地缓存和对象存储之间的调用关系，并能搭建本地实验、判断性能瓶颈和设计生产恢复流程。

## 📄 贯穿教程的问题

一个媒体处理系统有三类服务：

- 上传服务把原片写入 `/srv/media/inbox/M1001.mp4`。
- 转码服务读取原片，把结果写入 `/srv/media/output/M1001-720p.mp4`。
- 审核服务读取成片和 `/srv/media/review/M1001.json`。

服务运行在不同主机或 Pod 上，却要看见同一棵目录树。原片很大，缩略图和 JSON 很小；同一素材还可能被重新转码。整套教程围绕六个问题展开：

1. 普通路径怎样穿过 FUSE 到达 JuiceFS Client？
2. 文件名、权限、Chunk 映射和文件内容分别保存在哪里？
3. 默认写入为什么先上传数据，再提交元数据？
4. 缓存何时加速读取，何时造成放大或一致性变化？
5. FUSE、CSI、Hadoop SDK、Python SDK 和 S3 Gateway 应该怎样选？
6. 元数据引擎、对象存储或客户端异常时，怎样定位和恢复？

## 📄 先抓住四个责任边界

| 组件 | 在媒体案例中的职责 | 直接故障表现 |
| --- | --- | --- |
| 应用与内核 VFS/FUSE | 发起文件系统调用，把请求交给用户态客户端 | 挂载丢失、权限错误、系统调用卡住 |
| JuiceFS Client | 解析读写、访问元数据、切分数据、管理缓存和后台任务 | 客户端日志报错、请求延迟上升 |
| 元数据引擎 | 保存目录、inode、权限、锁、Chunk/Slice 映射和会话 | `ls/open/rename` 普遍变慢或失败 |
| 对象存储 | 持久保存 Block 的字节 | 大文件读写失败、吞吐下降、首读慢 |

本地缓存位于客户端一侧，保存从对象存储下载或刚上传的 Block。它能减少远程读取，却不取代元数据引擎和对象存储的持久化职责。

## 📄 一条最短心智链

```text
路径与权限 -> 元数据引擎
文件内容   -> Chunk / Slice -> Block -> 对象存储
重复读取   -> 客户端本地缓存命中时少访问对象存储
```

默认可靠写入还有一条关键顺序：

```text
客户端缓冲写入 -> Block 上传对象存储 -> 元数据提交新 Slice -> 其他客户端重新 open 后看见
```

`--writeback` 会把“元数据提交”提前到异步上传之前，因此本地暂存盘成为持久性链路的一部分。这个选项的性能收益与风险在 [一致性与故障边界](03-一致性与故障边界.md) 中展开。

## 📄 学习验收

完成教程后，不看原文画出下面两条链：

```text
读：open -> FUSE -> 元数据查询 -> Block 定位 -> 本地缓存或对象存储 -> read
写：write -> 内存缓冲 -> Block 上传 -> 元数据提交 -> close -> 其他客户端 reopen
```

然后回答：

1. 对象存储里为什么找不到名为 `M1001.mp4` 的原始对象？
2. `ls` 很慢但顺序读大文件很快，优先检查哪个组件？
3. 开启 `--writeback` 后客户端主机永久损坏，为什么对象存储可能缺少已经“写成功”的内容？
4. 只备份对象存储 Bucket，能否恢复原目录树？

## 📄 适用场景与边界

JuiceFS 适合多主机或多 Pod 共享文件、对象存储容量复用、大数据/AI 训练数据、媒体资产和备份归档等场景。它提供接近 POSIX 的文件接口，并通过元数据引擎协调共享命名空间。

下面这些工作负载需要先验证：极高频的随机小写、依赖特定本地文件系统 ioctl 的程序、要求数据库级事务语义的应用，以及对尾延迟极敏感却无法部署本地缓存的服务。兼容性以目标操作系统、FUSE 版本、JuiceFS 客户端版本和真实应用测试为准。
