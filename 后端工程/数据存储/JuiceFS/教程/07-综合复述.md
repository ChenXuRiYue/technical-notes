# 📌 JuiceFS 综合复述与场景推演

本篇不再引入新组件。先闭卷回答，再根据卡住的对象返回对应章节。能从证据推导下一步，比能背出名词更重要。

## 📄 补全一次默认写入

```text
应用 write
  -> 内核 ______ 把请求交给 JuiceFS Client
  -> 客户端按偏移定位 ______
  -> 一次连续写入形成 ______
  -> 持久化时拆成 ______ 并上传 ______
  -> 上传成功后提交 ______ 映射
  -> 其他客户端 close-to-______ 后看见新状态
```

参考答案：

```text
FUSE -> Chunk -> Slice -> Block -> 对象存储 -> 元数据 -> open
```

若分不清后三个对象，返回 [架构与读写路径](01-架构与读写路径.md) 的 Chunk、Slice 与 Block。

## 📄 推演一：路径快，内容慢

证据：

```text
两个客户端 ls /srv/media/output 都很快
open M1001-720p.mp4 很快
第一次顺序读取只有 80 MiB/s
第二次读取达到 1.8 GiB/s
元数据数据库 P99 正常
```

先预测瓶颈边界，再展开答案。

<details>
<summary>参考推理</summary>

路径与 `open` 快、元数据 P99 正常，元数据层不是首要嫌疑。第一次慢、第二次快说明本地缓存改变了数据路径。优先用 `stats` 对齐对象存储下载流量、缓存写入与应用吞吐，再检查客户端到 Bucket 的网络、下载并发和 readahead。第二次结果代表热读，不能证明对象存储能提供 1.8 GiB/s。

</details>

若答案只写“加缓存”，返回 [缓存与性能](04-缓存与性能.md) 的基线与观测顺序。

## 📄 推演二：文件存在，Block 不在

证据：

```text
上传节点开启 --writeback
应用 close 返回后 2 秒，节点磁盘永久损坏
其他节点 stat 文件成功
read 返回 I/O error
对象存储找不到对应 Block
```

参考推理：`--writeback` 先提交元数据，再从本地 `rawstaging` 异步上传。故障发生在上传完成前，因此目录与映射已经可见，持久 Block 却随本地磁盘丢失。应按数据完整性事件处理，从上游副本恢复，并重新评估是否允许该角色使用写回模式。

若认为“元数据存在就证明文件完整”，返回 [一致性与故障边界](03-一致性与故障边界.md) 的默认写入与写回对比。

## 📄 推演三：只丢了数据库

证据：

```text
对象存储跨区域副本完整
元数据数据库及其本地备份损坏
对象存储 meta/ 中有最近一次自动元数据备份
```

恢复链应该是：

1. 在隔离环境取得与备份兼容的 JuiceFS 客户端。
2. 把元数据备份 `load` 到空的元数据引擎。
3. 重新安全配置缺失的对象存储凭据。
4. 只读或隔离挂载，抽样和批量校验路径与文件内容。
5. 对比 RPO，确认最近备份之后的变化如何补偿。
6. 演练通过后，按审批流程切换正式客户端。

直接对 `chunks/` 猜测原文件名不构成可靠恢复。详细操作返回 [监控、备份与故障排查](06-监控备份与故障排查.md)。

## 📄 推演四：接入方式选择

为下面场景选择入口，并写出理由：

| 场景 | 首选方向 | 判断依据 |
| --- | --- | --- |
| 旧版 C++ 转码程序只接受本地路径 | FUSE | 保留 POSIX 路径接口 |
| Kubernetes 中多个 Pod 共享工作目录 | CSI Driver | 使用 PV/PVC 生命周期集成 |
| Spark 集群已统一 Hadoop FileSystem 配置 | Hadoop Java SDK | 与 JVM/Hadoop 生态直接集成 |
| Python/Ray 进程内读取，运行环境不能挂 FUSE | Python SDK / fsspec | 进程内直接访问 |
| 应用只实现了 S3 API | S3 Gateway | 保留应用现有对象接口 |

这不是永久答案。还要根据语义、性能、权限、版本和运维能力做目标环境验证。返回 [接入方式与生产部署](05-接入方式与生产部署.md) 查看完整边界。

## 📄 推演五：小文件增长

审核系统每天新增 500 万个 3 KiB JSON。一个月后总数据字节仍不算大，但 `create/stat/list` 延迟和元数据容量快速上升。

完整答案应包含：

- 总字节数不能代表文件系统操作成本；每个文件都有 inode、目录项和元数据操作。
- 用 `profile` 找慢操作，用 `stats` 与数据库指标确认元数据瓶颈。
- 评估目录分片、元数据引擎容量/吞吐和客户端并发。
- 在业务允许时，把不可变小记录合并为更合适的数据组织；需要独立更新的记录可转向数据库或表格式。
- 用相同输入与并发比较改造前后的 P95/P99、操作率、容量和对象请求量。

若只回答“扩容 Bucket”，返回 [缓存与性能](04-缓存与性能.md) 的小文件部分。

答案至少包含：FUSE 或 SDK、JuiceFS Client、元数据引擎、对象存储、Chunk/Slice/Block、默认先上传后提交、close-to-open、缓存和元数据备份。
