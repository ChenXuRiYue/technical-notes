# 📌 缓存、性能与小文件

转码服务第一次读取 20 GiB 原片时只有 300 MiB/s，第二次读取却达到数 GiB/s；与此同时，审核页面列出十万个缩略图很慢。两个现象来自不同路径：大文件首次读取依赖对象存储，目录和小文件操作更依赖元数据引擎。

学完本篇，你应该能用 `bench` 建立基线，用 `stats` 判断实时瓶颈，用 `profile` 找到慢操作，再决定是否调整缓存、预读、并发或业务文件布局。

## 📄 性能由四个乘区共同决定

| 维度 | 典型信号 | 主要组件 |
| --- | --- | --- |
| 元数据操作率与延迟 | `ls/stat/open/create` 慢 | 元数据引擎、网络、元数据缓存 |
| 数据吞吐与延迟 | 冷读、顺序写慢 | 对象存储、网络、上传/下载并发 |
| 客户端资源 | CPU、内存缓冲、缓存盘繁忙 | JuiceFS Client 与本机磁盘 |
| 应用访问模式 | 小文件、稀疏随机读、反复覆盖 | 应用、文件布局与缓存策略 |

任何“调大一个参数”的建议都必须先说明想改善哪一格，否则可能把瓶颈移到内存、缓存盘或对象存储请求费用上。

## 📄 三层读取缓存

一次读取大致按下面顺序尝试：

1. **内核页缓存**：已打开或近期读取的文件页，命中延迟最低。
2. **客户端进程缓冲**：承载读预取和待写数据，大小由 `--buffer-size` 等配置影响。
3. **客户端磁盘缓存**：保存下载过的 Block，受 `--cache-dir`、`--cache-size` 和剩余空间比例约束。
4. **对象存储**：缓存均未命中时获取持久 Block。

冷读表示所需数据尚未在这些本地缓存中；热读表示一个或多个缓存层命中。对比测试必须记录缓存状态，不能把第二次读取结果当成对象存储吞吐。

## 📄 Readahead 与 Prefetch

顺序读取时，客户端根据当前偏移提前下载后续 Block，称为 readahead。`--max-readahead` 限制最大预读窗口，实际并发还受缓冲区大小影响。

随机读取一个 Block 的小范围时，客户端可以异步下载整个 Block，称为 prefetch。它赌“相邻内容很快还会被读到”。这个猜测在 Parquet footer 或局部密集随机读中可能有效，在稀疏跳读超大文件时会产生读取放大。

| 访问模式 | 先考虑 | 需要防范 |
| --- | --- | --- |
| 连续扫描视频 | readahead、下载并发、对象存储带宽 | 缓冲区拥塞、挤压写入 |
| 反复读取模型或素材 | 本地缓存、`warmup` | 缓存盘容量与淘汰 |
| 稀疏随机读大文件 | 降低或关闭 prefetch | 整 Block 下载造成放大 |
| 单次 ETL 扫描 | 对象存储吞吐，按需弱化缓存 | 写缓存占用却没有复用收益 |

## 📄 小文件为什么贵

一万个 4 KiB JSON 的业务数据总量只有约 39 MiB，但每个文件都要创建目录项/inode、执行 `open/stat/close`，还可能产生独立小 Block 与远程请求。总字节数很小，操作次数却很大。

小文件问题要分两层处理：

- **元数据层**：提高元数据引擎并发与低延迟能力，减少不必要的目录遍历。
- **业务布局层**：在业务允许时，把不可变的小记录打包为更大文件或使用数据库/表格式；保留需要独立文件语义的对象。

“全部打包”也有边界：随机更新一个成员可能要求重写大包，单文件故障域和并发写协调也会扩大。选择以真实读写模式为依据。

## 📄 第一步：隔离环境建立基线

在独立测试目录运行，避免与生产文件混在一起：

```bash
mkdir -p /mnt/jfs/perf-lab
juicefs bench /mnt/jfs/perf-lab -p 4
```

`bench` 覆盖大文件顺序读写和小文件创建、读取、删除。`-p 4` 表示 4 个并发线程。结果只代表当前客户端、挂载参数、后端和测试并发；改变任何一项都应重新记录。

若只测小文件：

```bash
juicefs bench /mnt/jfs/perf-lab --big-file-size 0 -p 4
```

先在隔离环境确认测试空间、对象存储费用与清理行为，再对生产同构环境执行。

## 📄 第二步：运行中看哪一层忙

```bash
juicefs stats /mnt/jfs
juicefs stats /mnt/jfs -l 1
```

`stats` 按秒展示使用量、FUSE、元数据、Block 缓存、对象存储和客户端运行时指标。观察时同时运行一个可复现工作负载，并记录：

- 元数据操作延迟是否升高；
- 对象存储上传/下载流量是否达到预期；
- 缓冲区是否长期拥塞；
- 缓存命中与缓存盘 I/O 是否匹配；
- 应用吞吐变化是否与某一层同步。

## 📄 第三步：找到具体慢操作

```bash
juicefs profile /mnt/jfs
```

`profile` 基于访问日志聚合已完成操作，可以按 UID、GID、PID 过滤。它回答“哪些文件系统操作慢、由谁发起”，而 `stats` 回答“此刻哪类资源繁忙”。二者组合比只看 CPU 更接近因果链。

对于单个文件：

```bash
juicefs info /mnt/jfs/inbox/M1001.mp4
```

`info` 展示 inode、长度和对象映射，可用于确认碎片、Block 数量和路径是否符合预期。

## 📄 预热适合什么

训练任务或转码批次即将反复读取固定素材时，可以提前把数据下载到本地缓存：

```bash
juicefs warmup /mnt/jfs/inbox/batch-2026-08-27
```

预热用空间和对象存储流量换首轮读取延迟。数据只读一次、缓存盘比对象存储吞吐还低、或缓存很快被淘汰时，预热收益有限。

## 📄 参数调整顺序

1. 固定应用输入、并发、客户端规格和缓存状态，建立基线。
2. 用 `profile` 判断是元数据操作还是数据读写慢。
3. 用 `stats` 验证元数据、对象存储、缓冲和缓存盘中哪层饱和。
4. 一次只改一个参数或一组强相关参数。
5. 同时比较吞吐、P95/P99 延迟、CPU、内存、缓存盘、对象请求量和错误率。
6. 保留回滚配置，再扩大到灰度客户端。

P95/P99 是 95%/99% 请求不超过的延迟。平均值可能掩盖少量但影响用户的慢请求。

## 📄 先预测

一个作业对 1 TiB 数据只做一次顺序扫描，缓存盘容量 100 GiB。把 `--cache-size` 调到 1 TiB 会让它必然更快吗？

不会。数据没有复用时，缓存会增加本地写入和淘汰成本；缓存盘吞吐还可能低于对象存储。应先用 `stats` 比较对象下载、本地缓存写入和应用吞吐，再决定是否采用只缓存局部读取的策略。

改变条件：同一批 50 GiB 模型文件会被连续训练 20 个 epoch，且每台训练机有独立 NVMe。此时预热和足够的本地读取缓存更可能把后续 epoch 从远程读取变成本地读取。

## 📄 自我解释

用“第一次转码慢、第二次快”向同事解释冷读、热读和三层缓存，再说明怎样设计一个不自欺的对比实验。若答案里没有缓存状态、对象存储流量和相同输入条件，回到“建立基线”与“运行中观察”。

本教程没有在当前环境运行 JuiceFS 性能测试；命令按 2026-08-27 官方命令参考核对。测试结果必须在目标网络、元数据引擎、对象存储和客户端规格上重新采集。
