# 📌 接入方式与生产部署

本地实验只有一个客户端和 SQLite。生产媒体系统要让虚拟机、Kubernetes Pod 和离线计算任务共同访问数据，还要让元数据服务与对象存储跨单机故障继续工作。

学完本篇，你应该能根据应用接口选择接入方式，并写出一份包含元数据高可用、对象存储、凭据、缓存、监控、备份和恢复目标的上线清单。

## 📄 先选应用入口

| 接入方式 | 应用看到什么 | 适合 | 主要边界 |
| --- | --- | --- | --- |
| FUSE | 本机目录与 POSIX 文件 API | 虚拟机、物理机、传统程序 | 需要 FUSE 和挂载生命周期管理 |
| Kubernetes CSI Driver | Pod 中的 PVC 挂载目录 | Kubernetes 有状态或共享文件工作负载 | CSI、Kubernetes 与客户端版本要验证 |
| Hadoop Java SDK | `jfs://` 一类 Hadoop FileSystem 接口 | Spark、Hive、MapReduce 等 JVM 生态 | 依赖与 Hadoop 类路径需统一 |
| Python SDK / fsspec | Python 进程内文件 API | Ray、Python 数据处理、不便挂载 FUSE 的环境 | 只覆盖进程内接入，不给其他进程提供挂载点 |
| S3 Gateway | S3 API | 已经使用 S3 SDK 的应用与工具 | S3 API 语义不等于完整 POSIX |
| WebDAV | HTTP/WebDAV | 轻量文件共享与通用客户端 | 性能与语义受协议限制 |

选择从应用原生接口开始。传统程序已经使用本地路径时，FUSE/CSI 迁移成本最低；Spark 集群使用 Hadoop FileSystem 时，Java SDK 避免每个节点单独维护 FUSE；程序本来就使用 S3 API 时，Gateway 更自然。

## 📄 生产链路

```text
虚拟机 FUSE / Kubernetes CSI / Hadoop SDK
                    |
                    v
              JuiceFS Client
             /              \
            v                v
   高可用元数据引擎      对象存储 Bucket
   目录、inode、映射      Block 数据与元数据备份
```

客户端不通过一台中心 JuiceFS 数据服务器转发全部字节。每个客户端直接访问元数据引擎和对象存储，因此两套后端的网络、认证、吞吐和可用性都进入端到端 SLO。

SLO（Service Level Objective）是服务目标，例如 99.9% 挂载可用、P99 `open` 小于某阈值、单客户端顺序读达到某吞吐。目标必须结合真实工作负载测量。

## 📄 元数据引擎怎样选

SQLite 与 BadgerDB 适合单机实验，生产共享访问通常使用网络数据库。JuiceFS Community Edition 支持 Redis/Valkey、TiKV、etcd、MySQL/MariaDB、PostgreSQL 等，具体支持与最低版本以当前官方文档为准。

| 关注点 | 要提出的问题 |
| --- | --- |
| 延迟 | `open/stat/create` 的 P95/P99 能否满足应用？客户端与数据库是否同地域？ |
| 吞吐 | 峰值文件操作数、并发客户端和小文件增长率是多少？ |
| 高可用 | 主节点故障怎样切换？切换期间会拒绝、阻塞还是丢失已确认事务？ |
| 持久性 | 数据库自身怎样备份、复制和恢复？是否实际演练？ |
| 容量 | inode、文件名、扩展属性、Slice 与会话会占多少空间？增长怎样告警？ |
| 一致性 | 所选复制模式能否满足元数据事务要求？是否存在异步多主冲突？ |

Redis 作为元数据引擎时必须避免逐出 JuiceFS 元数据，官方要求 `maxmemory-policy noeviction`。选择任何引擎，都要使用专用命名空间/数据库，避免与业务缓存混用。

## 📄 对象存储怎样选

对象存储保存全部 Block，评估时同时看：

- 客户端所在网络到 Bucket 的吞吐、延迟、出口费用和限流。
- 服务端加密、版本控制、生命周期、跨区域复制与合规要求。
- 内网 Endpoint 与公网 Endpoint 的可达性；优先使用同地域内网链路。
- PUT/GET/HEAD/DELETE 请求费用，特别是大量小文件与随机读取。
- 存储类型是否能立即读取；归档层通常需要先恢复对象。

JuiceFS 内部管理对象键。不要让生命周期规则绕过 JuiceFS 元数据直接过期 `chunks/` 下的 Block，否则有效文件可能损坏。

## 📄 建卷命令的生产形状

下面只展示配置边界，不是可直接复制的生产值：

```bash
export META_PASSWORD_FILE=/run/secrets/jfs-meta-password
export ACCESS_KEY="${INJECTED_ACCESS_KEY}"
export SECRET_KEY="${INJECTED_SECRET_KEY}"

juicefs format \
  --storage s3 \
  --bucket https://media-prod.s3.example.com \
  --trash-days 7 \
  "rediss://metadata.internal:6379/1" \
  media-prod
```

优先使用云工作负载身份或短期凭据。必须使用静态凭据时，通过 Secret 文件或受控环境注入，避免把口令写进脚本、命令历史、Pod Spec 明文和 Git。

`format` 只执行一次。卷名、UUID、Block 大小、对象存储等配置会影响已有数据的解释和位置；变更前查询当前版本的 `juicefs config` 能力、兼容限制与恢复路径，不重复格式化同一元数据命名空间。

## 📄 客户端配置按角色分组

媒体系统可以有不同挂载角色：

| 角色 | 访问模式 | 配置重点 |
| --- | --- | --- |
| 上传节点 | 大文件顺序写 | 对象存储上传带宽、缓冲、失败重试 |
| 转码节点 | 大文件顺序读且可能复用 | NVMe 缓存、readahead、缓存容量 |
| 审核服务 | 小文件与目录读取 | 元数据延迟、目录规模、只读权限 |
| 运维节点 | 备份与检查 | 受控 Meta URL、审计、低业务干扰 |

不同角色可以调整缓存与后台任务，但同一卷至少保留一个允许执行后台任务的客户端。后台任务负责清理待删除对象、回收站、过期会话和自动元数据备份等工作。

## 📄 Kubernetes CSI 上线检查

CSI Driver 把 JuiceFS 卷集成到 Kubernetes PV/PVC 生命周期。上线前按目标版本的 [CSI 文档](https://juicefs.com/docs/csi/introduction) 完成：

1. 核对 Kubernetes、CSI Driver、JuiceFS Client 和内核/FUSE 兼容矩阵。
2. 把 Meta URL 与凭据放入受控 Secret，限制 Namespace 与 ServiceAccount 权限。
3. 建测试 StorageClass/PV/PVC，让两个 Pod 同时挂载并验证跨节点读写。
4. 重启业务 Pod、删除并重建挂载 Pod、驱逐节点，观察卷是否按目标时间恢复。
5. 验证缓存目录容量、宿主机磁盘压力与 DaemonSet/挂载 Pod 日志采集。
6. 灰度验证后再让生产 PVC 迁移，保留源数据回退路径。

静态 PV、动态供应、Mount Pod 等配置会随 CSI 版本和部署模式变化。本教程不固定一份容易过期的 YAML；以部署版本对应的官方清单为起点，并把最终渲染后的资源纳入代码审查。

## 📄 安全与租户边界

- 使用 Unix UID/GID、权限位和可选 ACL 控制文件访问，并确认容器内外身份映射一致。
- 元数据数据库和 Bucket 使用最小权限网络策略，只允许 JuiceFS 客户端与运维身份访问。
- 对象存储凭据泄露可绕过挂载层，因此还需 Bucket 策略、审计、密钥轮换和服务端加密。
- 元数据备份可能包含目录名等敏感信息；备份位置、保留和访问也要纳入安全策略。
- 生产与测试使用独立卷、数据库命名空间、Bucket 前缀和凭据。

## 📄 先预测

两个 Kubernetes Pod 能通过同一个 Bucket 访问对象存储，但各自使用不同的 SQLite 文件。它们会看见同一棵目录树吗？

不会。Block 数据共享了，目录项、inode 与 Block 映射却来自两份不同元数据。分布式共享需要所有客户端访问同一个受支持的网络元数据引擎命名空间。

改变条件：两个客户端共享元数据引擎，却分别配置到不同 Bucket。路径映射相同，但部分客户端无法在自己的数据后端找到映射指向的 Block。生产配置必须保证卷的元数据入口和对象存储配置一致。
