# data_mining_web 平台入口与启动流程

> 记录时间：2026-08-03  
> 项目：data_mining_web  
> 问题起点：理解 `web/main.py` 的入口、顶层执行顺序，以及各个函数在服务生命周期中的作用。

## 项目现场

这是一个由 FastAPI 提供 HTTP 接口、由 Uvicorn 承载的 Python Web 服务。平台不是固定加载全部业务路由，而是通过环境变量 `SERVICE_ROUTER` 选择当前进程需要承载的业务模块。

主要文件：

| 文件 | 当前职责 |
| --- | --- |
| `web/run_native.sh` | 使用 Uvicorn 启动 ASGI 应用 |
| `web/main.py` | 创建应用、动态注册路由、启动附加消费者和调度器 |
| `conf/config.py` | 根据 `ENV` 选择配置并完成敏感配置解密 |
| `conf/dev.py` | 开发环境配置和 `SERVICE_ROUTER` 来源 |
| `conf/preview.py` | 预发环境配置 |
| `conf/production.py` | 生产环境配置 |
| `web/router/<module>/<router>.py` | 对外 HTTP 接口定义 |

## 入口结论

这个项目没有传统的 `main()` 函数。入口是 `web/main.py` 中创建的 ASGI 应用对象：

```python
app = FastAPI(...)
```

`web/run_native.sh` 使用下面的形式启动：

```bash
python -m uvicorn main:app
```

`main:app` 可以拆成：

```text
main  -> 导入 main.py 模块
app   -> 从模块中取得名为 app 的 ASGI 对象
```

该脚本需要在 `web/` 目录语境下运行。如果从项目根目录启动，对应的模块路径通常写成 `web.main:app`。

## 执行顺序

必须区分两个阶段：Python 模块导入阶段，以及 FastAPI 应用生命周期阶段。

```text
Uvicorn 导入 web/main.py
  -> 执行 import
  -> 导入 conf.config，加载并解密 settings
  -> 定义 quick_tune_recover
  -> 定义 lifespan
  -> 创建 FastAPI app
  -> 读取 SERVICE_ROUTER
  -> 动态导入 Router 并注册到 app
  -> 按 Router 条件启动消费者和调度器
  -> 按 ENABLE_AUTH 注册认证中间件
  -> 模块导入完成，Uvicorn 获得 app
  -> Uvicorn 触发 lifespan 启动阶段
  -> 初始化 Nacos
  -> 恢复 QuickTune 中断任务
  -> 初始化 trigger_conf 本地仓库
  -> lifespan 执行到 yield，开始接收请求
  -> 服务停止后从 yield 继续执行关闭逻辑
```

### 模块导入阶段

执行 `from conf.config import settings` 时，`conf/config.py` 的顶层代码会立即运行：

1. 读取 `ENV`。
2. 选择开发、预发或生产配置。
3. 解密数据库、Redis、Nacos 等配置。
4. 设置 `PROJECT_ROOT`。
5. 暴露全局 `settings`。

因此配置加载不是 `lifespan` 的一部分。配置解密失败时，FastAPI 应用还没有创建。

Python 遇到函数定义时只创建函数对象，并不会立即执行函数体。因此 `quick_tune_recover()` 和 `lifespan()` 都是在后续阶段被调用。

### 应用生命周期阶段

`FastAPI(lifespan=lifespan)` 只是把生命周期函数交给 FastAPI。模块导入完成后，Uvicorn 才会触发生命周期协议。

`lifespan` 以 `yield` 为边界：

```text
yield 之前  -> 应用启动逻辑
yield 时    -> 应用处于服务状态，可以处理请求
yield 之后  -> 应用关闭逻辑
```

## 函数作用

### `quick_tune_recover()`

位置：`web/main.py:31`

作用：

1. 检查 `SERVICE_ROUTER` 是否包含 `quick_tune_mining.quick_tune`。
2. 按需导入 `QuickTuneTaskService`。
3. 调用 `resume_parsing_tasks()` 恢复上次中断的数据解析任务。

这是条件启动逻辑，不加载 QuickTune 路由时不会导入对应 Biz。

### `lifespan(app)`

位置：`web/main.py:41`

启动阶段依次完成：

1. 记录进程 PID。
2. 初始化 Nacos 客户端。
3. 调用 `quick_tune_recover()`。
4. 确保本地 `trigger_conf` Gerrit 仓库已初始化。

`trigger_conf` 初始化失败只记录警告，不阻止应用启动。当前关闭阶段只记录日志，没有实际释放资源。

### `app`

位置：`web/main.py:69`

`app` 不是函数，而是 FastAPI 应用对象，负责承载：

- API 路由；
- CORS 中间件；
- 可选认证中间件；
- OpenAPI 文档；
- 应用生命周期。

## 动态路由机制

例如：

```text
SERVICE_ROUTER=image_mining.search,label_mining.search,package.package
```

每个配置项会被转换成完整模块名：

```text
label_mining.search
  -> web.router.label_mining.search
```

然后通过 `importlib.import_module()` 导入。每个被加载的 Router 模块都需要暴露：

```python
router
router_openapi
```

二者都会注册到同一个 `app`。这让同一份代码可以按部署单元选择业务能力，但也意味着路由字符串、Python 模块路径和部署配置必须保持一致。

## 路由触发的附加服务

部分路由不只注册 HTTP 接口，还会在 `web/main.py` 顶层启动后台组件：

| 路由条件 | 附加行为 |
| --- | --- |
| `package.package` 且 `CONSUMER_FLAG=true` | 创建多个 RocketMQ 消费者并启动数据包调度器 |
| `vehicle_cloud_trigger.router` 或 `vehicle_cloud_trigger.message_report` | 启动车云 Trigger 调度器 |
| `dynamic_rule_mining.auto_schedule` | 启动动态规则例行化调度器 |
| 任意 `dynamic_rule_mining.*` | 启动动态规则公共 PKL 同步调度器 |

三个 `_scheduler_started` 变量只能避免同一进程内因多个路由匹配而重复启动，不能跨进程去重。

## 关键认知

### 模块导入不只是“加载代码”

这个文件包含明显的顶层副作用：

- 配置解密；
- Router 模块导入；
- 消费者实例化；
- 调度器启动；
- 中间件注册。

因此仅仅导入 `web.main` 就会执行上述逻辑，并不需要先收到 HTTP 请求。

### 消费者和调度器早于 `lifespan`

当前代码先在模块顶层启动部分消费者和调度器，之后 Uvicorn 才触发 `lifespan` 并初始化 Nacos。阅读启动问题时不能把所有初始化都理解成 `lifespan` 内的统一顺序。

### 多 Worker 会重复执行顶层逻辑

Python 模块单例和 `_scheduler_started` 标志只在单个进程内有效。如果部署使用多个 Uvicorn Worker，每个 Worker 都会独立：

- 导入 `web.main`；
- 创建自己的 `app`；
- 执行路由注册；
- 运行符合条件的顶层启动逻辑；
- 执行自己的 `lifespan`。

是否会造成消费者或调度任务重复，需要结合实际部署的 Worker 数量和外部幂等机制判断。
